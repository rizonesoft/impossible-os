**Why findings land here instead of being fixed.** The run is explicitly NOT permitted to modify its own control plane while unattended -- `.claude/hooks/**`, `.claude/skills/**`, `scripts/overnight/**`, `.githooks/**`, `.claude/settings.json` -- nor the RECEIPT SURFACE (`Makefile*`, `scripts/build.sh`, the ABI generator), which `receipt_surface_guard.py` enforces: build/verification machinery whose content the run's own receipts are computed over must not drift while nobody is watching, because a subtly wrong `build.sh` keeps producing green receipts that no longer mean what they say. Ordinary work is unaffected: kernel code, tests, docs and TODO files are fixed in place as normal.

**Self-improvement is the point of this file, not a side effect.** When the run hits a runner defect -- a gate that misfires, a wedge, a flow inefficiency, an evasion it was tempted into -- the finding is RECORDED HERE in the same turn it is observed, then the run continues.

**What to write.** One item per finding, house style: what was observed live (timestamps, file:line), the mechanism confirmed at source, and what it would cost or risk. A projection is not a finding. If a fix is obvious, describe it -- do not apply it. Lead line <= 250 chars; body as sub-bullets, none over 1,000 chars.

**Scope:** runner flow, gates, wedges, correctness of the run machinery. Cost/token findings go to the newest [`token-saver-vNN.md`](../token-saver/token-saver-v06.md) instead.

- [ ] Control-plane tooling tests flap between runs of the SAME tree: 5 assertions failed across two `test-tooling.sh` runs and passed on the next with zero intervening edits to the code they cover
      Observed live 2026-07-31 during TODO-04 §37's review, in two separate clusters, both under `scripts/overnight/run-artifact.sh`:
      - **10:05 run** -- `section_commit_gate: small-section commit with full evidence allows (want 0, got 2)`, 1/974 failed. Re-run at 10:05:44 with no edits in between: 974/974 PASS.
      - **10:24 run** -- `phase1_evidence_block: 2-Read PASS path`, `phase1_evidence_misslog: 2 Reads PASS without emit`, `phase1_evidence_block: infrastructure path coverage`, `phase1_evidence_block: malformed-input resilience`, 4 of 13 failures. The other 9 were genuine (my own harvester change) and I fixed them; these 4 I did not touch, and they passed at 10:31 and 10:43.
      - **Mechanism, partially confirmed at source.** Both groups build an isolated fixture repo under `mktemp -d`, copy the hooks into it and `pushd` there (`scripts/test-tooling.sh:4396-4434` for the phase1 group, the `$GATE_REPO` setup for the gate group). But the hooks do NOT resolve state from the fixture path the test wrote -- `phase1_evidence_gate.py:105-111` derives its root from `git rev-parse --show-toplevel` run in the CURRENT directory, and reads `.claude/state/skill-progress.json` under whatever that returns. Whether the temp dir resolves to the fixture repo, to the real repo, or to nothing is a property of the environment, not of the test.
      - **Leading hypothesis, NOT yet confirmed:** the live `.claude/state/` files the runner itself mutates (`last-codex-review.json`, `skill-progress.json`) are being read by these tests, so a verdict depends on what the run is concurrently doing. The 10:24 cluster sits minutes after a three-leg Codex dispatch wrote review state. Confirming it needs one run with the live state files held fixed and one with them mutating; I did not run that experiment because the fix is control-plane and out of bounds unattended.
      - **Cost/risk.** These are the gates that protect the section-commit and evidence contracts, so a flapping verdict is the worst place to have one: a real regression in them reads as "the usual flake", and a green run proves less than it appears to. It also burned two full suite re-runs this section purely to decide whether my own change was at fault.
      - **If the mechanism is confirmed, the fix is to make the fixture repos authoritative** -- have the tests point the hooks at the fixture root explicitly rather than relying on cwd-derived resolution -- so no control-plane test can read live runner state.
      - **Third cluster, 2026-07-31 11:47 (attended), and it WEAKENS the live-state hypothesis.** An operator-side full-suite run scored 983/984 with the sole failure `scripts/lsp-mcp/tests/test_bridge.sh` (98/99 sub-tests). The run's OWN suite had scored that file `PASS (99/99)` at 11:04 and 11:25 on the same tree, and re-running it alone at 11:52 with zero intervening edits gave `99/99 sub-tests PASS`.
      - **Why that matters for the diagnosis above:** `test_bridge.sh` is NOT a hook test and reads no `.claude/state/` file, so the "hooks resolve state from cwd and pick up live runner state" mechanism cannot explain it. Two candidate causes remain and they are not exclusive: HOST CONTENTION (this failure landed while the run held a 4-leg `test-smoke-matrix.sh` plus `build.sh clean`, so a timing-sensitive sub-test can lose its window) and a genuinely order/timing-dependent sub-test. The fixture-authority fix would not have prevented this one.
      - **Cheap discriminator before any fix:** run the full suite twice on a quiet host and twice while a smoke matrix runs, and record which files flap in which condition. If the flapping set grows under load but not on a quiet host, the defect is contention-sensitivity in the tests, not state leakage, and the repair is to serialize or bound the affected sub-tests rather than to re-root the fixtures.

- [ ] The attended-repair and ship-rollover gates can deadlock each other: the run refuses to roll over on an attended session's dirt AND on its unpushed commits, while pre-push refuses to push while the run has WIP
      Observed live 2026-07-31 11:37-11:41 on `run-20260731-095007`, during an attended repair of the R4 defect above, with all four states hit inside four minutes.
      - **11:37:52 -- dirt blocks the rollover.** `rollover REFUSED (checkpoint not verified): tree not clean (2 blocking change(s): .claude/hooks/runner_bash_guard.py [tracked-source], .claude/hooks/websearch_offload_gate.py [tracked-source])`. The attended edits were mid-flight; `_ROLLOVER_AUTOGEN` tolerates only auto-gen / xref-repair / gotcha-prune, correctly.
      - **11:39:48 -- committing does not clear it.** `rollover REFUSED: 1 commit(s) not pushed`. So an attended commit parked locally blocks the ship exactly as dirt does; "commit now, push at the boundary" is not a safe attended pattern.
      - **11:40 -- and the push has its own gate.** `.githooks/pre-push` REFUSES while the run has work in flight ("the CI-parity gate compiles the WORKING TREE... a failure would name your push and mean nothing"), pointing at the rollover boundary. Each gate is individually right; together they define a window an attended repair must fit entirely inside.
      - **The window is real but narrow**, and it is the same instant the run is trying to use: the run's tree is clean exactly at its ship boundary, which is also when it wants to roll over. A repair that takes longer than the run's retry cadence turns into the refuse-fix-refuse cascade the receipt note warns about (this one cost 3 refused rollover attempts).
      - **Escape that worked, and why it is honest here:** for a change touching NO `BUILD_INPUT_PATHS` entry (`src include user resources tools Makefile scripts/build.sh boot.conf`) the CI-parity gate cannot be measuring anything about the change, so `SKIP_CI_PARITY=1 SKIP_CI_PARITY_REASON='run owns tree'` skips a check that had nothing to verify. It is NOT honest for a code change, which is precisely when the run is most likely to be holding WIP.
      - **Proposed shape (control plane, not applied):** teach the pre-push gate the same build-input test the receipt machinery already uses -- when the push touches no build input, run the runner suite and skip only the CI-parity compile, so a docs/hooks/capture-file repair never has to choose between an unverified push and blocking the run's rollover.
