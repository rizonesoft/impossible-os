- [x] **Page-table use-after-free across reap + fork/exec: a task runs on a REAPED process address space and panics.**
  **MOVED 2026-07-27 to `02-kernel-core/TODO-21-process-model-extensions.md` section 19 (`task_exec` Commit Point and Kernel-Stack Reclamation).** This is a live kernel memory-safety bug, not a runner concern, and the sequencer does not traverse THIS file -- so it could never be scheduled from here no matter how well documented it was. Section 19 already owns the reap / exec / kernel-stack lifetime defects it belongs with, is the only open section in TODO-21, and TODO-21 is the sequencer's NEXT file. The full diagnosis (both file:line sides of the race, the ASCII-register evidence, the deterministic repro, and the do-NOT-pin-QEMU warning) moved with it.
  **This item previously read "kernel hangs under QEMU 8.2.2 (stock Ubuntu LTS)". That framing was WRONG and is corrected here so it cannot mislead a later session. The kernel does not hang, and QEMU is not the defect.** It PANICS, on a latent lifetime race that 8.2.2's timing happens to expose. Everything below is measured.
  **The panic.** `[PANIC] USER_ACCESS_VIOLATION` with `RIP=0x62226100202020  RBP=0x4B4F2D45504950  CR3=0x16CD000  RSP=0xA6C4C0`, preceded by `mm: pf: user fault ... code=0x14` and a first-chance `0xc0000005` dispatch. Two registers hold ASCII: `RBP` little-endian is `"PIPE-OK"`, a pipe test's buffer, and `RIP` is spaces plus `a"b`. The process is fetching instructions out of recycled data.
  **Why it is a use-after-free of the user PML4.** The transition ring records **PID 12** running at `cr3=0x16CD000  rsp=0xA6C4B0`. The panic context carries the SAME `CR3` and an `RSP` 16 bytes up the SAME stack, while the line immediately before the fault is `sched: PID 13 -> entry 0x800000` and earlier in the boot `task: PID 12 reap cleanup` already ran. So a live task is executing against a reaped task's page tables, whose frames have since been recycled for other allocations. Free side: `vmm_destroy_user_pml4` (`src/kernel/mm/vmm.c:1209`); reap side: `src/kernel/sched/task.c:3479`. Open question for the fix: whether reap can free a PML4 while a task still holds that CR3, or whether fork/exec can adopt a recycled one.
  **Why it looked like a hang for so long.** `scripts/test.sh` waits for a test-summary line, and a panicked kernel never prints one, so a panic is indistinguishable from a hang from outside the guest. That is why raising the CI timeout never helped (300s -> 1200s got LESS far: 2428 serial lines/guest `3.180` versus 2397/`3.170`, both stopping at the same guest timestamp -- the tell that it was neither slow nor progressing). The timeout bump was reverted.
  **QEMU 8.2.2 is the TRIGGER, not the cause.** Same kernel, same flags, same host: `/usr/bin` 8.2.2 (`Debian 1:8.2.2+ds-0ubuntu1.17`, byte-identical to CI's) panics deterministically; `/usr/local/bin` 10.2.1 and KVM both complete 25474 kernel + 16 user tests. That is the signature of a timing-sensitive race one emulator hides, exactly the class CLAUDE.md's bare-metal-first rule exists for. Do NOT close this by upgrading or pinning CI's QEMU -- that would delete the only environment currently exposing the bug.
  **Repro (deterministic, ~3 min).** `PATH=<dir-with-8.2.2>:$PATH FORCE_TCG=1 bash scripts/test.sh SUITE=quota QUIET=1`, then grep the serial log for `USER_ACCESS_VIOLATION` rather than waiting for the timeout. Note a PLAIN 8.2.2 boot passes and reaches `C:\>` and idles at HLT -- only `test=1` (which runs the fork/exec suites) reproduces it, so the smoke test would report green and prove nothing.
  Fixing this should turn CI green on its own: it is the sole cause of the red `Build Impossible OS` job.
