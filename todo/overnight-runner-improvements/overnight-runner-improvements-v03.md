## Doc bugs that cost real turns

- [ ] **The convergence gate is documented as `bash <a python file>` in three skills; FOURTH recorded recurrence, and the failure mode silently defeats the gate.**
  Observed live 2026-07-28 14:13:58 on the second canary: the run issued `bash .claude/hooks/review_convergence.py should-redispatch 'todo/00-infrastructure/TODO-04-usermode-test-framework.md#20' design`, it failed, and the run re-issued it with `python3` four seconds later, noting "the skill's `bash review_convergence.py` invocation is wrong -- it's a Python file". One wasted turn, and only because the run happened to notice.
  **The silent-failure path is the real cost.** `review_convergence.py` carries `#!/usr/bin/env python3`, so `bash` fails with "syntax error near unexpected token" and **exit 2**. The gate's contract is exit 1 = CONVERGED (skip) and exit 0 = redispatch, so an exit 2 fail-opens to REDISPATCH. A run that does NOT notice the error therefore re-dispatches a full Codex round that the gate would have suppressed, and reports nothing wrong. This is the mechanism `live-gotchas.md` already recorded on 2026-07-17 in exactly those words.
  **It has now been logged four times and never fixed at source:** `live-gotchas.md` entries dated 2026-07-15, 2026-07-17 and 2026-07-25 (the last one covering `review_round_guard.py` too), plus this live occurrence. Two of those entries carry expiry dates (2026-08-17, 2026-09-01) and will silently lapse, taking the only surviving record with them. A gotcha that has recurred four times is not a gotcha, it is an unfixed bug.
  **Where the wrong shape is written** (`bash` on a Python file, both verbs): `review-todo-section/SKILL.md:46`, `codex-fix-review/SKILL.md:83`, and `overnight-sequencer/SKILL.md:157-161`. The same file also documents `bash .claude/hooks/review_round_guard.py`, which has the identical defect.
  **NOT fixed during this canary, deliberately.** `overnight-sequencer/SKILL.md` is FLOW-CRITICAL control plane (verified: `control-plane-match.sh --flow-critical` matches it; the other two skills do not), and patching it mid-run would make the canary stamp cover a skill the run never used -- the same reasoning this repo already applied to `arm-sequencer.sh` in v02. A partial fix of only the two non-flow-critical files would leave the sequencer's own copy wrong, which is incoherent. Land all three together after the stamp, and add a lint check so the shape cannot come back: any `bash <path>.py` in `.claude/` or `scripts/` documentation is a defect, since a `#!/usr/bin/env python3` file is never runnable by bash. That check is what turns this from a fifth gotcha into a closed item.
  XREF: `token-saver/token-saver-v02.md` (item: "DETERMINED + FIXED 2026-07-28: the convergence gate was not mis-keyed") -- that item found the gate suppressed 0 of 4 rounds and fixed the four unscoped review kinds. This is the OTHER half of the same symptom: even a correctly-scoped gate suppresses nothing when the caller invokes it in a way that always exits 2.

## The shared working tree blocks the operator outright (new argument for the worktree split)

Both items below were hit live within four minutes on 2026-07-28's second canary, and neither is a cost or an attribution argument. `token-saver-v02.md` measured the contamination COST at 0.7% of a night and concluded the cheap fixes were sufficient on cost grounds; that conclusion stands and is not contradicted here. These are a different class: the shared tree makes operator verification impossible while a run is active, and the failure mode pushes the operator toward disabling the very gate that exists to catch what a green local suite misses.

- [ ] **The `pre-push` CI-parity gate builds the WORKING TREE, so an operator cannot push ANYTHING while a run is mid-section -- not even a markdown-only commit.**
  Observed 2026-07-28 14:25. A commit touching one markdown file was refused by the pre-push gate with `[FAIL] Build failed`. The commit was fine; the build was not, because the gate compiles the working tree and the run had 232 insertions across five kernel files half-written in it (`include/kernel/sched/syscall.h`, `include/kernel/sched/task.h`, `src/kernel/mm/heap.c`, `src/kernel/mm/pmm.c`, `src/kernel/sched/task.c`). A section under construction does not compile, by definition, for most of its life.
  **Why this is worse than an inconvenience.** The documented escape is `SKIP_CI_PARITY=1`, and the gate's own doctrine explains why reaching for it is dangerous: CI-parity exists because a SYS_EXEC timing bug survived **297 commits and a green local suite**, and the gate is REQUIRED (not opt-in) precisely because "CI already gates PRs" is the assumption that failure disproved. So the shared tree creates steady pressure to disable the one gate the repo learned the hard way to keep. An operator who pushes during a run either waits hours for a clean boundary or defeats the gate.
  Fix directions: (1) the worktree split, which removes the shared tree and therefore both this and the item below at once; (2) failing that, have the pre-push gate verify the COMMIT being pushed (a temporary checkout or `git stash`-equivalent of foreign changes) rather than whatever happens to be in the tree -- correct in its own right, since a gate that tests unstaged third-party edits is not testing what it is about to publish; (3) cheapest stopgap, teach the gate to DETECT an active run (the launch lockfile at `.claude/overnight/launch.lock`, or `sequencer-run.json.active`) and refuse with "a run owns this tree, push at a rollover boundary" instead of an opaque build failure that reads as the operator's own bug.

- [ ] **Operator and run share `build/`, so an operator's verification run writes a verdict the run may read as its own.**
  Observed immediately after the item above: the refused push left `=== BUILD FAILED ===` in `build/build.log` at 14:25:22 while the run was still editing at 14:25:55. CLAUDE.md instructs every builder to check exactly that line (`tail -1 build/build.log` must show `=== BUILD OK ===`), so for the window between an operator's gate run and the run's next build, the run can read a FAILED verdict for a build it never invoked, against code it had not finished writing. The reverse direction is equally available: a run's build result can satisfy an operator who never built.
  Not observed to have misled the run this time -- it was mid-edit and rebuilt afterwards, which overwrites the file -- so this is recorded as a live hazard with a demonstrated mechanism, not as an incident with damage. **Recorded honestly: the operator (this session) caused it**, by attempting a routine push while the run held the tree. That is the point: it needed no carelessness, only a push at the wrong moment.
  Same fix ordering as above. The worktree split gives the run its own `build/` and closes this outright; short of that, an operator should treat `build/` as run-owned for the duration and not invoke any build (including indirectly, via a push gate) while `launch.lock` is held.

## `build_offload_reminder.py`: two verified defects, both hit live

- [ ] **False-positive BLOCK: any read-only command naming a `*.sh` script immediately before a suite script is misread as INVOKING it.**
  Hit live 2026-07-28 14:28 by a plain `grep -n "check-abi\|gen-user-abi" scripts/build.sh scripts/test.sh` -- a read-only search, blocked with exit 2 and the reroute message telling it to re-issue through `run-artifact.sh`. Wrapping a grep in the build wrapper is meaningless, so the only exits are rephrasing or giving up.
  **Mechanism, confirmed at source.** `_SCRIPT_RES[0]` (`build_offload_reminder.py:66`) is `\b(?:bash|sh)\s+...`. In `scripts/build.sh scripts/test.sh` the `\b` is satisfied by the DOT inside `build.sh` -- `.` is a non-word character, `s` is a word character -- so the regex reads the tail of one filename as the shell that invokes the next. Every `*.sh` path ends in `sh`, so ANY command mentioning two suite scripts in sequence trips it, as does `ls -la scripts/build.sh scripts/test.sh`.
  **It is also the only pattern of the three that violates the file's own stated design.** Patterns 2 and 3 both prefix with `_CMD_POS` (`(?:^|[;&|(]\s*)`), and the header comment says the intent is to match "the script path at a COMMAND position ... so a quoted mention mid-string does not trip the block". Pattern 1 has no command-position anchor at all.
  **Fix, verified before filing:** replace the leading `\b` with a negative lookbehind, `(?<![.\w])(?:bash|sh)\s+`. Checked against seven shapes -- it silences `grep ... build.sh test.sh` and `ls -la build.sh test.sh` while still catching `bash scripts/test.sh`, `sh scripts/build.sh`, `/bin/bash scripts/test.sh` and `time bash scripts/test.sh`. A plain `_CMD_POS` prefix would be wrong here, because it would stop matching the legitimate `time bash ...` and `/bin/bash ...` forms.
  **Severity is raised by the response, not the frequency: this BLOCKs (exit 2), it does not warn.** A false positive that only warns costs a line of noise; one that blocks costs a turn and, for a command the model cannot rephrase, can wedge. The repo's own reminder hooks (`cd_prefix_reminder`, `todo_wrap_reminder`) are warning-only precisely because the command they flag is correct -- here the command is not merely correct, it is not even the thing being flagged.

- [ ] **The offload gate keys on GLOBAL run state, so an interactive operator session is judged as the overnight run and blocked by its cost gates.**
  Same incident: the block above fired on an OPERATOR session, not the run. `build_offload_reminder.py:140` returns `bool(st.get("active")) and st.get("phase") == "SECTIONS"`, read from `.claude/state/sequencer-run.json` -- there is no check that the session issuing the command IS the run. So while a run is in SECTIONS, every interactive session in the repo inherits its phase gates, including the BLOCK above and the offload rerouting whose entire rationale ("91 in-context build/test runs floods the overnight context") is about the RUN's context, not an operator's.
  This is the same shared-state family as the two items above: the run and the operator share the working tree, `build/`, and now the control state that hooks branch on. The other hooks in the tree do distinguish -- `run_phase_guard.handle_stop()` returns early via `is_headless()` precisely so "an interactive operator session is never trapped" -- so the discriminator exists and this hook simply does not use it.
  Fix: gate on `is_headless()` (or the launcher's `OVERNIGHT_SEQUENCER_RUN=1` env marker, which the arm drop-in sets and an operator shell never has) in addition to the run-state check. Cheap, and it makes the hook's blast radius match its stated rationale. Worth auditing the other hooks for the same omission at the same time rather than fixing this one in isolation.
