  **Where the wrong shape is written** (`bash` on a Python file, both verbs): `review-todo-section/SKILL.md:46`, `codex-fix-review/SKILL.md:83`, and `overnight-sequencer/SKILL.md:157-161`. The same file also documents `bash .claude/hooks/review_round_guard.py`, which has the identical defect.

Land all three together after the stamp, and add a lint check so the shape cannot come back: any `bash <path>.py` in `.claude/` or `scripts/` documentation is a defect, since a `#!/usr/bin/env python3` file is never runnable by bash. ## The shared working tree blocks the operator outright (new argument for the worktree split)

Both items below were hit live within four minutes on 2026-07-28's second canary, and neither is a cost or an attribution argument. `token-saver-v02.md` measured the contamination COST at 0.7% of a night and concluded the cheap fixes were sufficient on cost grounds; that conclusion stands and is not contradicted here. These are a different class: the shared tree makes operator verification impossible while a run is active, and the failure mode pushes the operator toward disabling the very gate that exists to catch what a green local suite misses.

- [ ] **The `pre-push` CI-parity gate builds the WORKING TREE, so an operator cannot push ANYTHING while a run is mid-section -- not even a markdown-only commit.**
  Observed 2026-07-28 14:25. A commit touching one markdown file was refused by the pre-push gate with `[FAIL] Build failed`. The commit was fine; the build was not, because the gate compiles the working tree and the run had 232 insertions across five kernel files half-written in it (`include/kernel/sched/syscall.h`, `include/kernel/sched/task.h`, `src/kernel/mm/heap.c`, `src/kernel/mm/pmm.c`, `src/kernel/sched/task.c`). A section under construction does not compile, by definition, for most of its life.
  **Why this is worse than an inconvenience.** The documented escape is `SKIP_CI_PARITY=1`, and the gate's own doctrine explains why reaching for it is dangerous: CI-parity exists because a SYS_EXEC timing bug survived **297 commits and a green local suite**, and the gate is REQUIRED (not opt-in) precisely because "CI already gates PRs" is the assumption that failure disproved. So the shared tree creates steady pressure to disable the one gate the repo learned the hard way to keep. An operator who pushes during a run either waits hours for a clean boundary or defeats the gate.
  **Severity corrected 2026-07-28 16:03, downward: this is DELAY plus loss of on-demand verification, not publication failure.** The four commits held back by this block reached the remote anyway when the run made its own atomic ship push at §20 -- the operator's commits ride out on the run's next push, having been verified by the run's pre-push gate against a coherent complete tree. So an operator is not permanently blocked and the gate does still run over the operator's content. What remains real is that the operator cannot verify or publish ON DEMAND for the length of a section (about two hours here), and that the visible failure is an opaque `[FAIL] Build failed` naming the operator's own push rather than the run's in-flight code. Recorded rather than left overstated.
  **A sharper variant of the same hazard, observed at 15:59.** A rollover requires content-bound build/test/smoke receipts, and the run spent ~4 minutes regenerating them after a correct refusal ("the kernel rebuilt after my last smoke run"). An operator commit landing inside that window moves HEAD and can invalidate receipts the run has just paid for, producing a SPURIOUS refusal -- the operator manufacturing the exact wedge class that `08735ee2` was written to remove. This session deliberately held its commits until the rollover completed for that reason. The receipt window is short and invisible from outside, which is what makes it dangerous: there is no signal an operator can check that says "receipts are in flight, do not commit".
  **CORRECTED 2026-07-28 20:03, narrower than filed.** The receipt-window claim above overstated the risk for TODO-only commits. `scripts/overnight/receipts.py:46` fingerprints `BUILD_INPUT_PATHS = src, include, user, resources, tools, Makefile, scripts/build.sh, boot.conf` -- `todo/` is NOT among them, so a commit touching only `todo/**.md` cannot invalidate a build/test/smoke receipt. The 17:32 incident was therefore the CLEAN-TREE gate rejecting a DIRTY file, not a stale receipt: committing was always safe and leaving the file uncommitted was the actual hazard. The receipt-window caution stands only for commits touching a build-input path, which an operator rarely makes mid-run. Recorded because the original wording would have taught the opposite and more damaging habit -- hold the commit, leave the tree dirty, block the rollover.
  Fix directions: (1) the worktree split, which removes the shared tree and therefore both this and the item below at once; (2) failing that, have the pre-push gate verify the COMMIT being pushed (a temporary checkout or `git stash`-equivalent of foreign changes) rather than whatever happens to be in the tree -- correct in its own right, since a gate that tests unstaged third-party edits is not testing what it is about to publish; (3) cheapest stopgap, teach the gate to DETECT an active run (the launch lockfile at `.claude/overnight/launch.lock`, or `sequencer-run.json.active`) and refuse with "a run owns this tree, push at a rollover boundary" instead of an opaque build failure that reads as the operator's own bug.

- [ ] **Operator and run share `build/`, so an operator's verification run writes a verdict the run may read as its own.**
  Observed immediately after the item above: the refused push left `=== BUILD FAILED ===` in `build/build.log` at 14:25:22 while the run was still editing at 14:25:55. CLAUDE.md instructs every builder to check exactly that line (`tail -1 build/build.log` must show `=== BUILD OK ===`), so for the window between an operator's gate run and the run's next build, the run can read a FAILED verdict for a build it never invoked, against code it had not finished writing. The reverse direction is equally available: a run's build result can satisfy an operator who never built.
  Not observed to have misled the run this time -- it was mid-edit and rebuilt afterwards, which overwrites the file -- so this is recorded as a live hazard with a demonstrated mechanism, not as an incident with damage. **Recorded honestly: the operator (this session) caused it**, by attempting a routine push while the run held the tree. That is the point: it needed no carelessness, only a push at the wrong moment.
  Same fix ordering as above. The worktree split gives the run its own `build/` and closes this outright; short of that, an operator should treat `build/` as run-owned for the duration and not invoke any build (including indirectly, via a push gate) while `launch.lock` is held.

## `build_offload_reminder.py`: two verified defects, both hit live

- [ ] **False-positive BLOCK: any read-only command naming a `*.sh` script immediately before a suite script is misread as INVOKING it.**
  Hit live 2026-07-28 14:28 by a plain `grep -n "check-abi\|gen-user-abi" scripts/build.sh scripts/test.sh` -- a read-only search, blocked with exit 2 and the reroute message telling it to re-issue through `run-artifact.sh`. Wrapping a grep in the build wrapper is meaningless, so the only exits are rephrasing or giving up.
  **Mechanism, confirmed at source.** `_SCRIPT_RES[0]` (`build_offload_reminder.py:66`) is `\b(?:bash|sh)\s+...`. In `scripts/build.sh scripts/test.sh` the `\b` is satisfied by the DOT inside `build.sh` -- `.` is a non-word character, `s` is a word character -- so the regex reads the tail of one filename as the shell that invokes the next. Every `*.sh` path ends in `sh`, so ANY command mentioning two suite scripts in sequence trips it, as does `ls -la scripts/build.sh scripts/test.sh`.
  **It is also the only pattern of the three that violates the file's own stated design.** Patterns 2 and 3 both prefix with `_CMD_POS` (`(?:^|[;&|(]\s*)`), and the header comment says the intent is to match "the script path at a COMMAND position ... so a quoted mention mid-string does not trip the block". Pattern 1 has no command-position anchor at all.
  **Fix, verified before filing:** replace the leading `\b` with a negative lookbehind, `(?<![.\w])(?:bash|sh)\s+`. Checked against seven shapes -- it silences `grep ... build.sh test.sh` and `ls -la build.sh test.sh` while still catching `bash scripts/test.sh`, `sh scripts/build.sh`, `/bin/bash scripts/test.sh` and `time bash scripts/test.sh`. A plain `_CMD_POS` prefix would be wrong here, because it would stop matching the legitimate `time bash ...` and `/bin/bash ...` forms.
  **Fix it surgically -- do NOT disable this hook.** Four minutes after the false positive, at 14:32:32, the SAME hook fired a TRUE positive on the run: `bash scripts/test.sh SUITE=exec 2>&1 | grep ...`, a genuine bare suite invocation in the main context, which it blocked and the run rerouted through `run-artifact.sh` within six seconds. So one incident of each kind was observed within four minutes, on the same hook, on the same day. The hook is earning its place; only pattern 1's missing anchor is wrong, and the verified fix above leaves every true-positive shape matching.
  **Severity is raised by the response, not the frequency: this BLOCKs (exit 2), it does not warn.** A false positive that only warns costs a line of noise; one that blocks costs a turn and, for a command the model cannot rephrase, can wedge. The repo's own reminder hooks (`cd_prefix_reminder`, `todo_wrap_reminder`) are warning-only precisely because the command they flag is correct -- here the command is not merely correct, it is not even the thing being flagged.

- [ ] **The offload gate keys on GLOBAL run state, so an interactive operator session is judged as the overnight run and blocked by its cost gates.**
  Same incident: the block above fired on an OPERATOR session, not the run. `build_offload_reminder.py:140` returns `bool(st.get("active")) and st.get("phase") == "SECTIONS"`, read from `.claude/state/sequencer-run.json` -- there is no check that the session issuing the command IS the run. So while a run is in SECTIONS, every interactive session in the repo inherits its phase gates, including the BLOCK above and the offload rerouting whose entire rationale ("91 in-context build/test runs floods the overnight context") is about the RUN's context, not an operator's.
  This is the same shared-state family as the two items above: the run and the operator share the working tree, `build/`, and now the control state that hooks branch on. The other hooks in the tree do distinguish -- `run_phase_guard.handle_stop()` returns early via `is_headless()` precisely so "an interactive operator session is never trapped" -- so the discriminator exists and this hook simply does not use it.
  Fix: gate on `is_headless()` (or the launcher's `OVERNIGHT_SEQUENCER_RUN=1` env marker, which the arm drop-in sets and an operator shell never has) in addition to the run-state check. Cheap, and it makes the hook's blast radius match its stated rationale. Worth auditing the other hooks for the same omission at the same time rather than fixing this one in isolation.

## The documented hook opt-out silently fails on the commonest shape there is

- [ ] **`SKIP_*=1` is not detected when the command contains a heredoc whose body has an apostrophe, so a legitimate opt-out is BLOCKED while being told to use the opt-out it just used.**
  Hit live 2026-07-28 19:45 attempting to stage a finding while `section_review_required.py` gated the session on the RUN's un-stamped ship. `SKIP_REVIEW_HOOK=1 cp /dev/null <path>` worked; `SKIP_REVIEW_HOOK=1 tee <path> <<'"'"'EOF'"'"' ... EOF` with prose in the body was BLOCKED, twice, with the message telling the caller to set the very variable that was already set.
  **Mechanism, confirmed at source and by isolation.** `_skip_env._scan_inline()` (`.claude/hooks/_skip_env.py:80`) runs `shlex.split(cmd, posix=True)` over the WHOLE command string and, on line 81-82, returns `{}` on `ValueError`. An ASCII apostrophe inside a heredoc body is an unbalanced quote to `shlex`, so it raises "No closing quotation" and the opt-out silently disappears. Isolated by differential test: heredoc + plain body -> detected; heredoc + `v01'"'"'s lesson` -> NOT detected; heredoc + a Unicode apostrophe -> detected; apostrophe inside double quotes without a heredoc -> detected. It is specifically the ASCII `'"'"'` in a heredoc.
  **Blast radius is every gate that uses the shared helper**, not one hook: `read_skip_envs` is the common path for `SKIP_REVIEW_HOOK`, `SKIP_SKILL_STEP_BLOCK`, `SKIP_PHASE1_BLOCK`, `SKIP_RUNNER_SUITE`, `SKIP_HOOK_AUDIT` and the `SKIP_REVIEW_PIPELINE` batch alias. And the triggering shape is not exotic -- it is how prose reaches a command at all. Commit messages, TODO edits and doc writes are heredocs, and English contains apostrophes; the runner authors all three constantly. A run that legitimately needs an opt-out and happens to be writing prose gets blocked, retries, and is told each time to do what it is already doing.
  **This also explains, and supersedes, an earlier operator note** that recorded the symptom as "hook opt-out env vars must prefix the sole command, not follow `&&`". That rule is not the mechanism: `SKIP_REVIEW_HOOK=1 cp ... && echo ...; git log ...` works fine with two control operators. The real discriminator is the apostrophe-in-heredoc, which is why the earlier rule appeared to work sometimes and not others.
  **Fix, verified over six cases before filing:** keep the current `shlex` path, and on `ValueError` (or an empty result) fall back to a regex scan of the LEADING env-prefix only -- `^\s*((?:[A-Za-z_][A-Za-z0-9_]*=\S*\s+)+)` -- parsing assignments from that span alone. Checked: it recovers the heredoc+apostrophe case and a two-variable prefix, preserves the plain and heredoc-plain cases, and crucially does NOT create false positives (`echo SKIP_REVIEW_HOOK=1`, and a command with an apostrophe but no opt-out, both stay undetected). Scanning only the leading prefix is also more correct in principle than tokenizing an entire command whose tail is arbitrary data.
  Severity: HIGH for the unattended run, because the failure is silent, self-contradicting, and lands precisely when the run is trying to unblock itself.

- [ ] **`_skip_env.py` is in NEITHER control-plane manifest, so the helper every `SKIP_*` gate depends on can be changed with no gate firing.**
  Found while diagnosing the opt-out defect above: piping `.claude/hooks/_skip_env.py` to `control-plane-match.sh` returns nothing, and `--flow-critical` returns nothing. Every review-pipeline gate routes its opt-out through `read_skip_envs()` in this file, so a change here can silently disable -- or silently universalise -- the escape hatch on `SKIP_REVIEW_HOOK`, `SKIP_SKILL_STEP_BLOCK`, `SKIP_PHASE1_BLOCK`, `SKIP_RUNNER_SUITE` and `SKIP_HOOK_AUDIT` at once, while the runner test suite and the canary requirement both stay unarmed.
  **This is the same hole, in the same shape, that was closed for `.claude/settings.json` earlier the same day** (`overnight-runner-improvements-v02.md`, "Control plane: `.claude/settings.json` is in NEITHER manifest"). That item's reasoning transfers without modification: the manifest lists the gate FILES but not the machinery deciding whether a gate applies. The defect above is the proof it matters -- one line in this helper changes the effective behaviour of six gates, and nothing in the control plane would notice.
  Fix: add `.claude/hooks/_skip_env.py` to `control-plane-manifest.txt`. Decide deliberately on `control-plane-deterministic.txt`; by the manifest's default-conservative rule it should start flow-critical, since "an opt-out stopped working" is exactly the failure an attended canary exists to catch. Audit the other shared `_`-prefixed helpers (`_review_kind.py`, `_codex_dispatch.py`, `_advisory_budget.py`, `_heuristic_misses.py`) for the same omission in the same pass rather than one at a time.
