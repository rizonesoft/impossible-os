# Overnight Runner v04 -- 3-Day Canary Findings (3-day canary, armed 2026-07-28)

Findings from the 3-day unattended canary armed 2026-07-28. This file is a CAPTURE surface, not a work queue: it sits outside the sequencer's traversal, so nothing here is implemented by the run.

**Why findings land here instead of being fixed.** The run is explicitly NOT permitted to modify its own control plane while unattended -- `.claude/hooks/**`, `.claude/skills/**`, `scripts/overnight/**`, `.githooks/**`, `.claude/settings.json` -- and, since 2026-07-30, the RECEIPT SURFACE as well (`Makefile*`, `scripts/build.sh`, the ABI generator), enforced by `receipt_surface_guard.py`. Over three days with nobody watching, a bad edit to a gate or the sequencer skill is how a run becomes unrecoverable, and the runner suite gate runs at commit but cannot judge intent. Ordinary work is unaffected: kernel code, tests, docs and TODO files are fixed in place as normal, and the run SHOULD keep doing what it did on 2026-07-28 when it root-caused and fixed `test-smoke-matrix.sh` destroying its own leg logs.

**What to write.** One item per finding, in the house style: what was observed live (with timestamps and file:line), the mechanism confirmed at source, and what it would cost or risk. A projection is not a finding. If a fix is obvious, describe it -- do not apply it.

**Scope:** runner behaviour, gates, wedges, flow. Cost findings go to [`token-saver-v04.md`](../token-saver/token-saver-v04.md) instead.

**Predecessor:** [`overnight-runner-improvements-v03.md`](overnight-runner-improvements-v03.md) is the implementation list that preceded this canary; five of its six items shipped before the arm.

- [x] **The self-modify boundary is drawn by DIRECTORY, not by blast radius, so the run can rewrite the build and ABI machinery its own verification depends on -- unattended and inside the rules.**
  Observed live 2026-07-29 12:50-12:51, ~14 hours into the 3-day canary. After a lexical bug "bit four consecutive rounds (R3 context, R4 splice, R5 comment ordering, R6 header-name)", the run correctly stopped patching corners and replaced a hand-rolled lexer with a byte-exact comparison -- good root-cause judgment. But the blast radius of that refactor is much larger than the boundary anticipated: in the same session it has `scripts/build.sh`, `Makefile`, `scripts/gen-user-abi.py`, `include/kernel/abi_hash.h` and `user/include/abi_numbers.h` modified, 12 dirty files in all.
  **None of those is inside the boundary, and one of them is a receipt input.** The doctrine armed with this canary names `.claude/hooks/**`, `.claude/skills/**`, `scripts/overnight/**`, `.githooks/**` and `.claude/settings.json`. Checked against the matcher, all five files above return "outside the boundary". Yet `receipts.py:16` fingerprints `BUILD_INPUT_PATHS = src include user resources tools Makefile* scripts/build.sh ...` -- so `scripts/build.sh` and `Makefile` are precisely what the run's own build/test/smoke receipts are computed over. The run may rewrite the thing its verification is anchored to, and the boundary permits it.
  **The failure mode is not a wedge, it is a silent loss of meaning.** A hook edit breaks loudly and immediately. A subtly wrong `build.sh` or ABI generator keeps producing green receipts that no longer mean what they say, for as long as the run continues -- and on a multi-day unattended arm that is a lot of sections shipped against a verification that drifted. Nothing observed so far suggests this HAS happened; the point is that the boundary would not have stopped it.
  **Do not fix by widening the directory list.** "Everything risky" is not enumerable by path, and a longer denylist would also have blocked the genuinely good refactor above. The shape that fits the evidence is to gate on the RECEIPT SURFACE rather than on directories: a change touching any `BUILD_INPUT_PATHS` entry that is also build/verification machinery (`scripts/build.sh`, `Makefile`, the ABI generator) is filed rather than applied while unattended, while ordinary `src/` and `user/` work stays untouched. That reuses a list the repo already maintains for exactly this "what does verification depend on" question, instead of inventing a second one that will drift from it.
  **Operator note for this canary:** the refactor landed and should be reviewed on its own merits when the run is disarmed -- it is deep, it is cross-cutting, and it was authored with nobody watching. It is not evidence of a defect, only of a boundary that did not consider it.
  **CLOSED 2026-07-30 by `receipt_surface_guard.py` (new PreToolUse hook on Edit/Write/MultiEdit).** It gates exactly the shape the item prescribed and nothing wider.
  - **The list is IMPORTED, not re-typed.** `BUILD_INPUT_PATHS` is loaded from `scripts/overnight/receipts.py` at call time, so the gate cannot drift from the list receipts actually fingerprint -- a test asserts the literal is absent from the hook, and it caught a copy in my own selftest fixture while being written.
  - **Machinery, not receipt inputs.** The gate fires on the INTERSECTION: `Makefile*` (including sub-Makefiles), `scripts/build.sh`, `scripts/gen-user-abi.py`, `scripts/abi-stamp-check.sh`, `tools/boot-info-manifest/*`. `src/`, `include/`, `user/`, `resources/`, `tools/` are receipt inputs but ordinary work and are never gated -- which is the whole reason this is not a wider denylist.
  - **The two GENERATED ABI headers stay ungated.** `abi_hash.h` and `abi_numbers.h` are outputs of the generator; gating them would block routine ABI work for no gain, since a wrong generator is the actual hazard.
  - **Unattended only, and file-don't-refuse.** Keys on `OVERNIGHT_SEQUENCER_RUN=1`, so an operator editing `build.sh` -- the intended repair path -- is never touched. The block message tells the run to FILE the change here and CONTINUE the section, not to abandon the work. Opt-out `RECEIPT_SURFACE_OVERRIDE=1`.
  - **Fail-OPEN on every error path**, because a guard that wedges the run it protects is worse than the risk it covers. 55/55 runner suite (new `test_receipt_surface_guard.py`), hook audit PASS, MANIFEST + control-plane manifest rows added.

- [x] **`build_offload_reminder` false-positives on `|` and `(` inside DATA, and the run has started contorting commands to evade it -- which is worse than the block.**
  Two live occurrences, 7 hours apart, both in the 3-day canary. **2026-07-29 23:47:52:** "False positive: the hook's `(`-prefixed command pattern matched `(scripts/test.sh` in my prose. Rewording those two mentions." **2026-07-30 06:35:26:** blocked while recording Codex findings to the ledger, because its argument contained the pipe-delimited string `"high|scripts/test-tooling.sh:7883|..."` -- ledger DATA, not a command.
  **The evasion is the finding.** At 06:35:35 the run got past it by splitting a string literal: `TT="scripts/test-tooling"".sh:7883"`. A gate that teaches the model to obfuscate its own commands has stopped guarding and started shaping behaviour, and every future reader of that line will wonder why it is written that way. It also cost three consecutive retries (06:35:26, :35, :41, :51) to land one ledger write.
  **Mechanism: `_CMD_POS` is too generous.** `_CMD_POS = (?:^|[;&|(]\s*)` treats `|` and `(` as command positions, which is right for a shell pipeline and wrong for a quoted argument -- the regex has no notion of quoting, so any `|scripts/test.sh` or `(scripts/test.sh` inside a string reads as an invocation. Reproduced against the live hook: pipe-delimited data MATCHES, paren-in-prose MATCHES, an assignment carrying pipe data MATCHES, while a real `bash scripts/test.sh` still matches correctly.
  **This is the THIRD shape in the same hook**, and the first two were found the same way -- by it firing on something harmless. `_SCRIPT_RES[0]`'s `\b`-satisfied-by-a-dot was fixed in `77d36c59`; `[1]`'s `(` and `|` are these two. Fixing them one shape at a time is not converging, which is itself the signal: the hook is pattern-matching a shell grammar it does not parse.
  **Proposed shape, and it is a rewrite not a patch.** Strip quoted spans before matching, or match only against the command's first token per control-operator segment, rather than adding a fourth special case. `shlex` is the obvious tool and the obvious trap -- `_skip_env` used it and lost the opt-out to an apostrophe in a heredoc (`326bc786`), so any tokenizer here needs the same fail-safe treatment: on a parse failure, fall back to NOT blocking. A cost gate that cannot parse the command must not be the thing that stops a run.
  **CLOSED 2026-07-30 -- rewritten, not patched.** `_match_suite_invocation` no longer regex-matches raw text. It splits on control operators that are OUTSIDE quotes, `shlex`-tokenises each segment, and identifies the command POSITIONALLY (skipping `VAR=` prefixes and transparent wrappers like `time`/`exec`), so a suite path inside an argument is structurally incapable of reading as an invocation.
  - **Both live false positives are now regressions**, along with the evasion shape `TT="scripts/test-tooling"".sh:7883"` -- which the gate no longer has any reason to provoke.
  - **Fail-SAFE as the item required**: an unbalanced quote or a `shlex` parse error yields NO match, never a block. That is the `_skip_env` lesson (`326bc786`) applied deliberately rather than rediscovered.
  - **Two coverage bugs surfaced while doing it**, both caught by the existing suite rather than by inspection: the wrapped route `run-artifact.sh <label> -- bash scripts/test.sh` must still see its INNER command or the compliance `follow` log silently reads zero; and a blanket recursion past `--` then broke `git log --oneline -- scripts/test.sh`, where `--` introduces a pathspec. The recursion is now scoped to the wrapper alone.
  - Real invocations still caught: interpreter, absolute path, `./` prefix, quoted path, env-prefixed, `make test`/`test-*`, through a pipeline and inside a subshell. `make test=1` still excluded.
