## What shipped in the 2026-08-10 close-out, and is therefore under test

- **`_review_pipeline_passthrough` sees through grouping.** `is_review_pipeline_passthrough` steps over leading `(` / `{` before applying its first-token allowlist, so the sequencer's own prescribed ship shape -- `( git push ... ; echo "rc=$?" ) &` -- is no longer refused by the gate its own doctrine has to satisfy. Closed five v13 items with one fix. Watch for: any shell form that reaches a program the allowlist would refuse.
- **Loop headers are deliberately still blocked**, and that is the security line: a `for i in $(...)` header runs a substitution before the body, so stepping into the body would allowlist a call on the strength of a program that is not the one that runs first. Pinned as a control. Watch for: pressure to widen it -- the sanctioned long wait already has allowed spellings.
- **A commit-message substitution gate.** `commit_msg_backtick_block.py` refuses a `git commit -m` whose double-quoted body carries an unescaped backtick or `$(`. It is a PreToolUse gate, NOT a `commit-msg` hook: bash substitutes at parse time, so a commit-msg hook receives the already-damaged text. Watch for: a false block on a legitimate message -- single quotes, `-F -` heredocs and escaped ticks are all unmatched.
- **Eight grouped doctrine rules** -- four probe-discipline in `implement-unit-tests`, four review-discipline in `review-todo-section`. Watch for: whether they change behaviour or just exist.
- **`section_review_required` is scoped to whoever shipped.** It exempts a session when a run is ACTIVE and this session is not it, using the same `OVERNIGHT_SEQUENCER_RUN` discriminator `build_offload_reminder` was given for the identical class in July. Watch for: a real section ship going unreviewed -- the run itself is never exempt, and with no run active nothing changed.

## What shipped in the 2026-08-10 carry-completion pass, and is therefore under test

Six v13 carries plus the CI repair. Every change below carries a refusal-direction control -- a case that must still be BLOCKED -- because a canary exercises the happy path at scale and structurally cannot exercise the refusal path, which is the entire purpose of a gate.

- **The identity-gate wedge is closed by teaching the gate about CHECK SETS.** `build.py` declares `EMITTED_ERROR_CATEGORIES`; `producer_differential.py` asks both trees, and a head-side refusal of the BASE corpus under a category that exists only at HEAD is a NEW CHECK -- that leg is unrunnable by construction, so it is skipped loudly while the head-corpus leg still runs. The alternative (differential the head corpus only, whenever the producer changed) was rejected: it disables the gate exactly when the producer moved, which is when it is most valuable. Watch for: the UNPROVEN banner persisting -- it means the last-gated SHA still predates the probe, and once it does not, that path should stop appearing. If UNPROVEN is still printing weeks from now, the base is not advancing and something else is wrong.
- **The declaration is bound to reality twice, and it immediately earned it.** `_assert_declared_categories` refuses at runtime any category not declared; test_build.sh s39g pins the declaration to a literal AST shape so it cannot compute itself from the emitters. Writing the declaration by `grep` produced SIX categories against a true set of TWELVE, and the runtime binding caught all six missing ones within one suite run. Watch for: someone adding a check and a category in one commit without the declaration -- the build fails loudly, which is intended, but the error must stay legible enough that the fix is obvious rather than tempting to suppress.
- **`identity-gate.sh` now has a LOCAL gate.** `.githooks/pre-push` runs it when the push touches the resolver closure, using the REMOTE OID as base -- so it adjudicates exactly the commits about to land, and is strictly conservative against CI's own (possibly wider) range. Conditional, so ordinary pushes pay nothing. Watch for: wall-clock on a closure-touching push. It stacks with the tooling suite and the CI-parity compile on the same push, which is precisely the combination that has blown the 10-minute tool wall before; `SKIP_IDENTITY_GATE=1` exists for that, and reaching for it often is the signal to reconsider the trigger.
- **A shell subshell does not outlive the tool call.** One doctrine line in the sequencer's wait discipline, reconciled explicitly with the sanctioned ship-push shape (which is fine because the run polls it from the same call) and naming `nohup`/`setsid`/`disown` as non-fixes. Watch for: the rule being read as "never background anything", which would push the run back to blocking pushes and cost more than it saves.
- **`skill_step_block` no longer judges a throwaway repo.** The commit's destination is resolved (`-C`, `--work-tree=`, `--git-dir=`, a leading `cd`, else the cwd) and compared against `CLAUDE_PROJECT_DIR`; every uncertainty fails CLOSED. Watch for: an unusual spelling of a real project commit resolving to something else and going ungated -- the refusal controls cover bare, chained and `-C`-at-project shapes, but the extraction is a parser and parsers meet inputs their authors did not.
- **`optout_env_prefix_block` catches an opt-out that will be silently dropped.** It reproduces `_skip_env._scan_inline`'s stop-at-first-token rule rather than approximating it, and a test asserts the two AGREE on the same input. Widening `_skip_env` to scan whole chains was rejected: stop-at-first-token is what stops an opt-out being armed from inside arbitrary data. Watch for: a false block on a legitimate chain. It fires only on a known key, only after a chain operator, only when that key does not also lead the command -- but it is a new gate on the single most common command shape in the repo, so a false positive would be felt immediately.
- **The tooling receipt can attest the bytes being PUSHED.** `check --commit <sha>` recomputes the same key over the surface AS COMMITTED, so the run's own later edits no longer void a receipt that validly describes the pushed commit. Watch for: this is the one change that can make a gate PASS more often, so it is the one to distrust. The controls that must never go green are a real committed tooling change, a different commit, and an unreadable commit; untracked files can never match a commit key and so fall through to running the suite.

## Filed by the 2026-08-10 attended carry-completion session

- [x] **A pre-push gate stack that exceeds the tool wall costs TWO full suite runs, and the receipt cannot break the loop when the fix itself touches `scripts/`.**
      Observed live 2026-08-10 while pushing this cycle's own work, twice in a row.
      - The mechanism, confirmed: `.githooks/pre-push` runs the tooling suite (~7 min), then the new identity gate (~1 min), then the CI-parity compile. A `git push` at the 10-minute tool wall is killed mid-suite, nothing is pushed, and the work is repeated on the next attempt. Measured: one push killed at 550s having completed nothing.
      - The receipt is the designed escape and it CANNOT apply here, which is the actual finding. `tooling-receipt.py:SURFACE` includes `scripts`, so any commit that fixes a tooling script invalidates the receipt for its own push -- and a close-out cycle consists almost entirely of such commits. The `check --commit` binding shipped this cycle does not help either: the pushed commit genuinely changed a surface file, so refusing is correct.
      - Second-order cost: the killed push's suite kept running and held `/tmp/impossible-os-test-tooling.<hash>.lock`, so the next out-of-band suite run waited on it rather than starting. The lock behaved correctly; the point is that a killed push leaves work in flight that the next attempt must wait out.
      - The working sequence, if this stays unfixed: run the suite out-of-band, write the receipt, THEN push. That is three operator steps for what should be one, and it is exactly the shape a run cannot perform for itself.
      - **DECIDED 2026-08-10: do NOT background it, and the reason is structural rather than a preference.** A pre-push hook's only power is that it BLOCKS. Backgrounded, it returns 0, the push lands, and the result arrives afterwards -- which is precisely what `build.yml` already does, since that workflow runs on `push: [main]` and invokes the identical `bash scripts/test-tooling.sh --quiet` on the identical commit (`build.yml:124`). A backgrounded local suite is a slower, CPU-consuming duplicate of an existing cloud job, so "background it" and "delete it" are the same decision: both accept the red-`main`-the-next-session-repairs failure the gate was added to stop (measured 2026-08-05: 4 red commits, ~10 min plus a re-run).
      - **Resolved by SCOPING plus a correction to how the push is issued, and the first characterisation of the residual as "narrow" was WRONG.** Measured after the fact: **17 of the last 40 commits touch `scripts/todo-graph/`**, and each of those trips both the pack's todo-graph leg and the identity gate (~632s), so the over-wall case is roughly 40% of recent pushes rather than an edge case. Scoping still fixed the genuinely common path (~790s -> 320s when neither nested suite is reachable); it just does not cover the case this repo hits most.
      - **The actual fix was already in the repo and this session failed to follow it.** The sequencer's ship sequence backgrounds the push and polls a log in a LATER call (`( git push ... ) & echo started`), which returns in milliseconds so the tool wall never fires. Both killed pushes on 2026-08-10 used `timeout 560 git push` -- FOREGROUND-waiting past the wall, which is the one shape that dies. Background-and-return is safe; background-and-wait is not, and the two were conflated. The unattended run was therefore never exposed to this; only attended sessions were.
      - Three alternatives were considered and rejected as not worth their blast radius: a post-commit background receipt-earning hook (would add ~13 min of CPU contention per surface-touching commit, and contention is what caused two of this session's three suite failures); a deferred gate blocking push N+1 on push N's result (adds nothing over CI, which already reports on push N); and deleting the gate outright.
      - Watch for: this being re-litigated. The backgrounding idea is intuitive and recurs precisely because the blocking cost is visible while the gate's prevention is not. The counter-argument is one fact -- CI already runs the same pack on the same commit -- and it is recorded here and in CLAUDE.md so the next session does not re-derive it.

- [x] **RESOLVED 2026-08-10 (same session): the pre-push tooling pack is now SCOPED, cutting a hooks-only push from ~790s to ~320s.**
      The fix for the item above, chosen over raising the tool wall because it reduces work rather than accommodating it.
      - Measured first, and the obvious hypothesis was WRONG: the pack has 637s of nominal `sleep` across 49 sites, which looked like the answer. Per-line timestamping showed the real cost is two NESTED suites -- `test_build.sh` at 252s and the lsp-mcp harnesses at 219s, 60% of an ~790s pack -- both invoked unconditionally (`test-tooling.sh:655`, `:790`). A hooks-only push reached neither and paid 471s for them.
      - `TEST_TOOLING_CHANGED_PATHS` is opt-in and the DEFAULT is the safety property: absent, empty or unreadable runs everything, so CI (which passes nothing) keeps full coverage and a scoping bug costs time rather than coverage. Verified: clean default run 1320/1320 in 801s, scoped hooks-only run 1320/1320 in 320s.
      - Triggers were derived by extracting every repo path each harness references, not guessed, and are deliberately generous: `.githooks/` is in the todo-graph trigger because its section-30 tests exercise commit ticks. Refusal controls in `test_tooling_scoped_suites.py` assert each trigger fires for every path class its suite reads; mutation-checked by narrowing a trigger and by flipping the empty-set fast path to skip -- each caught by the intended test.
      - Watch for: a trigger that is too narrow. Only that direction is silent, which is why the skip is NAMED in the summary and the notice is not suppressed by `--quiet` (the pre-push caller uses `--quiet`, which is exactly where reduced coverage matters).

- [ ] **Two suite tests read live repo STATE rather than the change under test, and both passed by luck until this session.**
      Observed 2026-08-10 while validating the scoping change; both were mine to fix, and one is still latent elsewhere.
      - `test-tooling.sh:10974` greps `scripts/` for a retired schema id and excludes only paths matching `test-tooling.sh`. A debug COPY at `scripts/.tt-debug.sh` carried the string, did not match the filter, and failed the suite. Arguably correct (a stray copy of a tooling script under `scripts/` is worth flagging) but the diagnosis cost a 13-minute run, because the failure names the id rather than the file that introduced it.
      - `test_receipt_commit_binding.test_wrong_or_unreadable_commit_fails_closed` asserted `--commit HEAD~1` fails. That holds only when the previous commit touched a `SURFACE` path -- and SURFACE excludes `todo/` and `COUNT.md`, which is most of what this repo commits. A todo-only commit at HEAD made HEAD and HEAD~1 surface-identical, so validating both was CORRECT and the test was wrong. Repaired to CONSTRUCT a differing commit and assert its own premise is non-vacuous.
      - The shared lesson, and why this is filed rather than closed: a test whose fixture depends on unrelated repo history is testing the history. The first one is still shaped that way.
      - Also confirmed: editing the tree WHILE the suite walks it produces failures that look like real regressions. Two of this session's three suite failures were the session's own concurrent edits. The tooling receipt already refuses to be written in that state; the SUITE has no equivalent guard.
