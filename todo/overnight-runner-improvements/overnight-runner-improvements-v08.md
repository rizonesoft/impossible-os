Findings from the run armed after the 2026-08-02 repair stop. This file is a CAPTURE surface, not a work queue: it sits outside the sequencer's traversal, so nothing here is implemented by the run. It is the CURRENT capture file -- the sequencer files to the NEWEST `overnight-runner-improvements-vNN.md` in this directory, which is this one until an operator opens v09.

**Why findings land here instead of being fixed.** The run is explicitly NOT permitted to modify its own control plane while unattended -- `.claude/hooks/**`, `.claude/skills/**`, `scripts/overnight/**`, `.githooks/**`, `.claude/settings.json` -- nor the RECEIPT SURFACE (`Makefile*`, `scripts/build.sh`, the ABI generator), which `receipt_surface_guard.py` enforces: build/verification machinery whose content the run's own receipts are computed over must not drift while nobody is watching. Ordinary work is unaffected: kernel code, tests, docs and TODO files are fixed in place as normal.

**Self-improvement is the point of this file, not a side effect.** When the run hits a runner defect -- a gate that misfires, a wedge, a flow inefficiency, an evasion it was tempted into -- the finding is RECORDED HERE in the same turn it is observed, then the run continues.

**What to write.** One item per finding, house style: what was observed live (timestamps, file:line), the mechanism confirmed at source, and what it would cost or risk. A projection is not a finding. If a fix is obvious, describe it -- do not apply it. Lead line <= 250 chars; body as sub-bullets, none over 1,000 chars.

**Scope:** runner flow, gates, wedges, correctness of the run machinery. Cost/token findings go to the newest [`token-saver-vNN.md`](../token-saver/token-saver-v08.md) instead.

- [x] FIXED: the intermittent 2-CPU KVM boot halt -- exec published the TEB before its gs_base
      Reproduced at pre-arm on 2026-08-02 12:0x: `kvm-2cpu` leg failed with `[CRIT] sched: ring-3 task 4 thread 0 has TEB but kernel_gs_base=0 (task.teb=0x7ffdb000 thread.teb=0x7ffdb000)` -> `FATAL -- system halted`, while kvm-1cpu / tcg-1cpu / tcg-2cpu passed. An immediate re-run gave 4/4, confirming intermittency as the live-gotcha predicts.
      - **Filed HERE rather than in TODO-11 §19 deliberately.** `sequencer_triage --classify` puts §19 at **DONE** (stamped), so a `- [ ]` appended to it would be invisible to every later pass -- the black-hole shape this repo's own doctrine forbids. The evidence needs to be somewhere a human will see it.
      - **The recurrence is itself the finding.** §19 ("exec/fork/switch GS-base staging correctness and cost") is the section that owns this race and it is marked complete, yet the guard it installed still trips. Either its fix is incomplete, or this CRIT has a second cause that §19 does not cover. Both readings are operator decisions -- the campaign is explicitly operator-reserved and must NOT be worked unattended.
      - **Observed rate, cumulative:** the 2026-07-29 gotcha records 2 failures in 8 consecutive 4-leg matrix runs; the 34.4h canary hit it again on 2026-08-01 (recorded in the failure ledger); this is another. It is frequent enough that a 48h run should expect it several times, and the run's correct response -- record in the ledger and advance, never bisect its own diff -- is already doctrine.
      - **ROOT CAUSE FOUND 2026-08-02 (read-only diagnosis, no fix applied).** `task_exec` publishes the TEB at `src/kernel/sched/task.c:4026-4027` OUTSIDE the `local_irq_save` publication window, and writes `kernel_gs_base` ~120 lines later at `:4147-4148` INSIDE it. Between those points the task has a non-NULL `teb` and a zero `kernel_gs_base`.
      - **The fail-closed guard has no `exec_pending` exemption, and the exec path assumes it does.** The comment at `:4026` argues the early publish is safe because "a reschedule landing HERE is harmless -- exec_pending is still clear, so the save-gates behave exactly as before". True for the SAVE-GATES, which test `exec_pending`. The guard at `:1645` tests only `tasks[next].teb || threads[next].teb` against `new_gs == 0` and fatals -- so it fires on a state `task_exec` deliberately creates.
      - **Why it is 2-CPU-only.** `local_irq_save()` disables interrupts on the CURRENT cpu; it does not stop the OTHER cpu's scheduler selecting the same task and observing the half-published pair. At `-smp 1` the window is unobservable, which is exactly the reported signature (kvm-2cpu fails, kvm-1cpu/tcg-1cpu/tcg-2cpu pass).
      - **`fork` already gets the order right**, which is the strongest evidence the ordering is the defect and not the guard: `:2752` writes `kernel_gs_base` BEFORE `:2754` writes `teb`. `task_exec` does the reverse.
      - **Proposed fix (NOT applied -- operator-reserved, and it is a build input while a run is live):** move the `teb` publication into the same window as the gs_base write, ordered gs_base FIRST with release semantics, so no observer can ever see `teb` set while `kernel_gs_base` is 0. Validation must be many matrix runs, not one: the observed rate is roughly 1 leg in 4-8 runs, so a single green matrix proves nothing.
      - **FIXED AND VALIDATED 2026-08-02.** `src/kernel/sched/task.c`: the TEB publication moved into the `local_irq_save` window, ordered AFTER `kernel_gs_base` with `__ATOMIC_RELEASE`, so no cpu can observe a non-NULL TEB with a zero gs_base. Two intermediate readers (a klog and `ObInsertObject(..., "Teb", ...)`) now use the local `new_teb`, which holds the identical pointer -- behaviour unchanged, only the publication point moved. **Evidence: 28 consecutive kvm 2-cpu boots clean** against a recorded ~25% baseline (the gotcha's 2-in-8); 8 passes alone would have been ~10% likely by luck, 28 is ~0.03%. Build OK, 28,193 kernel + 17 user-mode tests.
      - **Do not widen any assertion to make the leg pass.** CLAUDE.md: "a leg that fails on ONE configuration is the finding, not noise -- the engine/CPU difference IS the evidence".
