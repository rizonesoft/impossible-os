## Flow and concurrency

- [ ] **Concurrency: operator and runner share ONE index, so `git add -A` + `git commit` cross-contaminate constantly.**
  Measured 2026-07-28, attended canary run: FOUR cross-sweeps in about four hours, two in each direction. Runner swept operator work into its commits at `46b553a3` (took `scripts/test-tooling.sh`) and `5ec722df` (took `scripts/lint.sh` Check 19 + `scripts/todo-staged-check.py`). Operator swept ~18 files of the runner's in-progress section-20 work into `a0410d3d`, then a `git commit -o <paths>` attempt to split it failed to restrict and re-committed the same set. Content was never lost in any of the four; attribution was wrong every time, and each incident cost the other party turns to diagnose ("HEAD moved because the operator committed and pushed `c305c165` mid-session").
  Root cause is structural, not carelessness: one worktree means one index. `git add -A` stages whatever the other party has in flight, and even a plain `git commit` takes the whole index, so a correctly-scoped `git add` is still followed by an over-broad commit. `git commit -o <paths>` is the documented escape and did NOT restrict in practice; `git commit -F <file> -- <paths>` with an explicit `--` separator DID work and is the shape to use.
  Fix directions, cheapest first: (1) the runner stops using `git add -A` and stages explicit paths only -- it already computes its section file list, and this alone kills the runner-to-operator direction; (2) the runner commits via `git commit -- <paths>` with an explicit pathspec rather than a bare commit; (3) longer term, give the unattended run its own worktree (`git worktree`) so the indexes are physically separate.
  Until then the operator's rule of thumb, learned the hard way tonight: never leave work uncommitted while the run is active, and never commit while it has files staged. Those two rules conflict, which is itself the argument for the worktree split.

- [ ] **Flow: the rollover check calls its OWN tooling's writes "the operator's edit" and refuses indefinitely.**
  Observed live 2026-07-28 03:42, attended canary run. The run refused a verified rollover with: "Rollover is blocked by the operator's in-flight TODO-25 edit, which isn't mine to clean -- so continuing in-session per doctrine." No operator had touched TODO-25. The dirty content was four XREF line-number bumps (467->468, 302->303, 463->464, 464->465), every one pointing into TODO-21 -- the file the run had just edited for section 19, shifting those very lines. The run's own XREF/graph tooling produced them minutes earlier (`stranded_deferrals.py --owner` and `todo-graph/build-and-validate.sh`, both at 03:23), and the rollover check then read the resulting dirty file as a human's in-flight work and declined to touch it.
  Why this is worse than a one-off: the misattribution is SELF-SUSTAINING. The helper scripts run as part of the section pipeline, so every section that shifts a cross-referenced line re-dirties a TODO the run will again refuse to own, and the rollover never fires unless a human commits for it. On this run it took an operator commit (`0f4d6995`) to unblock, after verifying all four line numbers against their targets -- the stale ones pointed at unrelated items, so the repairs were correct and the run should simply have owned them.
  Not universal, which sharpens rather than weakens it: at 05:13 the same run hit the identical situation on TODO-07, said "these are line-number repairs caused by the single line I added", spot-verified one, and OWNED them. So the behaviour is inconsistent, and the fix is to make the owning path the only path.
  Fix direction: the rollover check must distinguish "dirty because MY tooling wrote it" from "dirty because a human is mid-edit". The run already knows which files its own scripts touched in this section (it invoked them); record those paths and let rollover stage-and-commit them as pipeline output. Anything else stays operator-owned and still refuses. A blunter fallback: treat a file whose diff is entirely XREF line-number bumps as pipeline output regardless of author.
  XREF: this is the concrete failure mode the v01 item "a REFUSED rollover must BLOCK starting the next section" assumes away -- here the refusal was SPURIOUS, so hard-blocking would have wedged the run on its own scripts' output.

- [ ] **Flow: three consecutive sections landed `[/]` partial, none `[x]`, so the canary ship criterion was never met.**
  Observed 2026-07-28: section 18 was already `[/]` on entry, section 19 went `[ ]` -> `[/]` at 03:41 ("the code fixes hold, but the section's own test checkpoint is unmet"), and section 20 was still `[ ]` after roughly three hours and 9+ review dispatches across two segments. Deferring on a real blocker is doctrine-correct and each individual decision was honest -- section 19 committed working code and declined to claim a ship it had not earned. The concern is the aggregate: a runner that defers every section makes progress on code while never closing a TODO, and the fixpoint it is driving toward is defined by closures.
  This is evidence FOR, not against, the v01 decision to not implement the `[/]`-partial ship path as written -- the problem is not that `[/]` cannot ship, it is that the test checkpoints are not being met. Investigate why before touching the ship path: is the checkpoint unreasonable, is the section oversized, or is the work genuinely incomplete?

- [ ] **Flow: `docs/test-coverage/coverage.{md,json}` re-dirty the tree on every test run for a TIMESTAMP alone, and that blocks rollover.**
  Observed 2026-07-28 across the TODO-21 section 19 run. The only diff after a suite run is `Generated: 2026-07-28 08:05 UTC (HEAD commit time)` -> `09:05 UTC`; the coverage counts themselves are unchanged. Because rollover requires a clean tree including tracked modifications, every rollover after a test run must first either commit a no-information timestamp bump or discard the files, and the run has to work out which. This session discarded them, which is correct but is a judgement call the runner should not have to make each time.
  Fix directions, cheapest first: (1) drop the generated-timestamp line from the emitted files, or move it into a gitignored sidecar -- the git commit time already carries that information, which is what the line is derived from; (2) failing that, have the generator write only when a COUNT changed, so an unchanged suite is a no-op; (3) failing both, teach the rollover check to treat a diff confined to that one line as pipeline output it may discard itself (same class as the XREF line-number bumps in the item above).

## Gates that passed while the image was broken

- [x] **A section shipped `[x]` claiming "SMOKE TEST PASSED" and the image FATALs 2.5s later. Both smoke markers precede the crash.**
  **Closed 2026-07-28 (`a6a2b828`) -- the GATE hole this item owns is fixed; the kernel defect is separate and still open (see below).** Four defects were found and fixed in `scripts/test-smoke.sh`, three of them beyond what this item originally described: (1) fail patterns are re-checked AFTER the grace window, so a crash past the prompt can no longer land in a blind spot; (2) generic fatal signals added -- `[CRIT]`, `FATAL -- system halted`, `system halted` -- where the list previously named only specific shapes (`[CRIT]` is safe to blanket-fail because `klog.h` defines it as the `LOG_FATAL` tag, "serial + framebuffer, then halt", and it appears zero times in a healthy log); (3) a shape assertion that the log ENDS clean, which catches fatal shapes nobody enumerated; (4) **the gate had never run SMP at all** -- there was no `-smp` flag, so QEMU defaulted to ONE cpu, and the section that changed a context-switch handoff was validated single-CPU in a project whose doctrine is "SMP-safe by default ... SMP from day one". Now `-smp 2` (override `SMOKE_SMP`), plus a `SMOKE_FORCE_TCG` escape since CLAUDE.md says TCG catches timing races KVM hides and there was previously no way to ask for that engine.
  Verified both directions: the operator's failing log now FAILs on two patterns plus the ends-clean check, a synthetic healthy log passes, and the live image still passes on KVM with 2 CPUs online and on forced TCG. The gate runs on the real runner path -- `implement-todo-section` invokes it, and the canary segment called it 6 times.
  **Residual gap, NOT closed by this fix, filed as its own item below:** the specific regression is WHPX-only and still does not reproduce on Linux KVM or TCG at either CPU count, so an overnight run on this host remains blind to that class.
  Reported by the operator 2026-07-28 from a WHPX boot of the post-canary image (`main@238c49f6`). The system halts launching `cmd.exe`: `[CRIT] sched: ring-3 task 4 thread 0 has TEB but kernel_gs_base=0 (task.teb=0x7ffdb000 thread.teb=0x7ffdb000)` followed by `[**] FATAL -- system halted`. That is a boot-to-userspace failure, not a degraded boot.
  **Why every gate was green.** `scripts/test-smoke.sh` PASSes on two sentinels, "Boot complete in" and the `C:` prompt. In the failing log the ordering is: `22.640 Boot complete in 14.860s`, `24.570 Command Prompt window opened`, `25.170 CRIT ... FATAL`. Both sentinels are satisfied roughly 2.5 seconds BEFORE the fatal, so the smoke test observes a healthy prefix of a run that then dies. TODO-21 section 19 therefore shipped `[x]` with a verification stamp citing a passing smoke test, truthfully, against a test that cannot see the failure.
  **The smoke test's own contract is the bug.** Its stated purpose in CLAUDE.md is to prove "the image actually boots to userspace"; the marker it uses proves only that the kernel reached a banner. `cmd.exe` is the first ring-3 process, so a crash there is exactly the failure the test exists to catch, and it lands after the sentinel. Fix directions: require the shell to survive N seconds past the prompt (the run already waits 3s for log flush, so the wall-clock cost is near zero); treat any `[CRIT]` / `FATAL --` / `system halted` line ANYWHERE in the captured log as a hard FAIL regardless of markers; and assert the log ENDS cleanly rather than merely contains the sentinels.
  **Not a theoretical gap -- it cost a real regression.** Section 19's commits touched the guarded path directly: `c64bec7c` changed 5 `kernel_gs_base` lines and `1bed1fdc` another 6. The CRIT guard itself is old (`cd77b635`, 2026-04-22), so this is a pre-existing invariant newly violated, not a newly added check. The run's own review even reasoned about the window ("a tick in that window switches the task in with `kernel_gs_base == 0`") and shipped anyway.
  **Canary implication, recorded rather than quietly dropped:** the 2026-07-28 canary stamp (`2454518f`) cites this section ship as its evidence. The ship was real and satisfied every gate that exists; the gates were insufficient. Whether the stamp should be re-recorded once the kernel defect is fixed is an operator decision -- flagged here so that it IS a decision and not an oversight.
  **Kernel-side owner required:** the `kernel_gs_base=0` defect is kernel work, not runner work, and must be reopened against `todo/02-kernel-core/TODO-21-process-model-extensions.md` section 19 (or a successor section) with this WHPX log attached. This item owns only the GATE hole.

- [ ] **Overnight validates on Linux only, so a WHPX/bare-metal-class defect can still ship `[x]` with every gate green.**
  Established 2026-07-28 while fixing the gate above. After adding SMP, generic fatal detection, the ends-clean assertion and a TCG escape, the actual regression STILL does not reproduce locally: under Linux KVM and under forced TCG, at 1 and at 2 CPUs, the run reaches the identical point (`PID 4`, `PEB=0x7ffde000`, `TEB=0x7ffdb000`) and survives. The operator's `run-qemu-kvm.bat` boot -- WHPX on Windows -- halts there every time. So the residual gap is not a missing assertion; it is the platform.
  Consistent with an already-documented gotcha: CLAUDE.md records that "CR3 reloads on WHPX can reset per-vCPU MSRs (re-program PAT after TLB flush)", and `kernel_gs_base` is an MSR. CLAUDE.md also already states that "Verified on QEMU is necessary but not sufficient" -- this incident is the first time that gap is known to have cost a shipped section stamp rather than a near-miss.
  Two candidate directions, deliberately not chosen here because the trade is the operator's: (a) treat a section whose diff touches SMP / scheduler / MSR / per-CPU paths as REQUIRING an operator boot before its stamp, which makes those sections need a human and slows unattended completion; or (b) accept the gap explicitly and make the section stamp name which platforms actually validated it, so "SMOKE TEST PASSED" stops reading as "boots to userspace" when it means "boots to userspace on Linux KVM". (b) is cheap and honest; (a) is stronger and costs autonomy.
  Whichever is chosen, the wording of the stamp is worth fixing regardless: the current phrasing invited exactly the reading that caused this.

## Control plane

- [ ] **Control plane: `.claude/settings.json` is in NEITHER manifest, so a hook can be disabled with no gate firing.**
  Verified 2026-07-28 by feeding the path to the matcher directly: `printf '.claude/settings.json' | control-plane-match.sh` and `... --flow-critical` both return NOTHING. The manifest lists 10 individual hook FILES (`run_phase_guard.py`, `section_commit_gate.py`, `sequencer_triage.py`, ...) but not the file that WIRES them. So an edit that neuters any of those ten -- or adds a new blocking one -- runs the control-plane suite gate zero times and leaves the canary stamp valid.
  This is not hypothetical. Commit `a1c3802b` tonight disabled a live PreToolUse BLOCK hook (`search_offload_gate`) by deleting five lines from `settings.json`. It happened to also touch the hook file, which is what pulled it into the audit; had the change been settings-only -- the natural shape for "turn this gate off" -- nothing would have fired. The same shape can raise a timeout, swap a matcher, or reorder a gate chain.
  Partial coverage that exists and is NOT sufficient: `scripts/audit-hooks.sh` runs at pre-commit whenever `.claude/hooks/**` or `.claude/settings.json` is staged, and checks MANIFEST.md rows. That catches an undocumented hook; it does not run the runner suite and does not re-arm the canary, which are the two things a control-plane change is supposed to trigger.
  Fix: add `.claude/settings.json` to `control-plane-manifest.txt`. Decide deliberately whether it also belongs in `control-plane-deterministic.txt` -- a wiring change is arguably provable by the deterministic suite plus the hook audit rather than by a watched run, but "a hook was silently unwired" is exactly the failure a watched run is for, so default-conservative (flow-critical, canary-requiring) is the safer starting point.

- [ ] **`arm-sequencer.sh` tail dies on EVERY default arm; root cause found 2026-07-28, fix not yet landed.**
  The script documents this as "Root cause still unknown" after the 2026-07-20 and 2026-07-24 arms. It is not intermittent. `write_sequencer_model_dropin()` ends each loop iteration with `[ -n "$ARM_EFFORT" ] && echo "Environment=OVERNIGHT_EFFORT=$ARM_EFFORT"`, the LAST command in a `{ ... } > file` group. `ARM_EFFORT` is empty by default (line 248, and `--effort inherit` empties it at 281), so the test is false, `&&` short-circuits, the group exits 1, and that status propagates group -> loop body -> `for` -> function return, where `set -euo pipefail` kills the script -- AFTER the file has been written, which is why every prior investigation blamed the next function.
  Blast radius: the dead tail skips `write_claude_token_dropin`, so the run falls back to the shared `~/.claude/.credentials.json` and re-enters the single-use-refresh-token race the long-lived token exists to end. That is the #1 historical run-killer, silently re-armed on every arm since 2026-07-20.
  Fix validated off-tree 2026-07-28 (`if` blocks instead of trailing `&&`): current tree dies rc=1 with the marker never printed, patched copy returns rc=0 with correct drop-in content. Not landed during the canary because `arm-sequencer.sh` is flow-critical and patching it mid-run would make the stamp cover an arm script the run never used. Land after the stamp, add a regression test (call the writer with `ARM_EFFORT=""` under `set -e`, assert rc=0 and both files present), and add a post-arm assertion that the effective unit environment carries the token `EnvironmentFile` and `MCP_NO_AUTO_CHROME` -- that property is deterministic, so it belongs in `control-plane-deterministic.txt` rather than behind another watched run.

- [ ] **Flow: a REFUSED rollover must BLOCK starting the next section, not "continue in-session" into it.**
  **DECISION 2026-07-27: BLOCKED-ON `token-saver-v01` T1-3 -- do not implement first.** Two reasons, both checked.
  (1) WEDGE RISK. A refused rollover means dirty tree / unpushed / missing receipts / unreceived review / live background job. Hard-blocking the next section leaves an unattended run with nowhere to go when it cannot self-clear the blocker -- it can neither rotate nor advance. The item's own escape ("or the section is deferred with its state") is a path that DOES NOT EXIST yet. Ship the block before building it and the result is a deadlock, not a guardrail.
  (2) OVERLAPPING BENEFIT. T1-3 (size-triggered mid-section rollover) attacks the same context balloon from the other side and CANNOT wedge, because it fires at safe boundaries by construction. If T1-3 lands and context still balloons at section boundaries, this item is justified on fresh evidence; if it does not, this item may be unnecessary.
  **Order of work when it is taken up: build defer-with-state FIRST, then the hard block. Never the reverse.** Also note the diagnosis predates R1 (`_ship_stamp_since`), which already catches the never-ATTEMPTED rollover -- so the remaining gap is narrower than the item text implies. Re-measure before building.
  The macro phase machine is rigid, but the per-section rollover cadence inside the SECTIONS phase is soft: `SKILL.md:314` says a REFUSED rollover means "finish/clean them and continue in-session," with no rule against advancing to the NEXT section first. Result (§12 -> §13, Codex log:1480): §12's rollover was refused (dirty tree / receipts), the worker advanced into §13 anyway, and context ran unbroken from §12's start through §13 -- the reset beat never fired, which is the balloon's boundary-side cause. Fix: a refused rollover HARD-BLOCKS the next section -- either the blockers get cleaned and the rotation fires, or the section is deferred with its state; never start a fresh section on an un-rotated context. Boundary-side complement to item 1 (size trigger = mid-section) and the split-enforcement item.
