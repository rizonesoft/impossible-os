# Overnight Runner Improvements v07 -- 24h Canary Findings (armed 2026-08-01)

Findings from the 24-hour canary armed after the 2026-07-31 repair stop. This file is a CAPTURE surface, not a work queue: it sits outside the sequencer's traversal, so nothing here is implemented by the run. It is the CURRENT capture file -- the sequencer files to the NEWEST `overnight-runner-improvements-vNN.md` in this directory, which is this one until an operator opens v08.

**Why findings land here instead of being fixed.** The run is explicitly NOT permitted to modify its own control plane while unattended -- `.claude/hooks/**`, `.claude/skills/**`, `scripts/overnight/**`, `.githooks/**`, `.claude/settings.json` -- nor the RECEIPT SURFACE (`Makefile*`, `scripts/build.sh`, the ABI generator), which `receipt_surface_guard.py` enforces: build/verification machinery whose content the run's own receipts are computed over must not drift while nobody is watching, because a subtly wrong `build.sh` keeps producing green receipts that no longer mean what they say. Ordinary work is unaffected: kernel code, tests, docs and TODO files are fixed in place as normal.

**Self-improvement is the point of this file, not a side effect.** When the run hits a runner defect -- a gate that misfires, a wedge, a flow inefficiency, an evasion it was tempted into -- the finding is RECORDED HERE in the same turn it is observed, then the run continues.

**What to write.** One item per finding, house style: what was observed live (timestamps, file:line), the mechanism confirmed at source, and what it would cost or risk. A projection is not a finding. If a fix is obvious, describe it -- do not apply it. Lead line <= 250 chars; body as sub-bullets, none over 1,000 chars.

**Scope:** runner flow, gates, wedges, correctness of the run machinery. Cost/token findings go to the newest [`token-saver-vNN.md`](../token-saver/token-saver-v07.md) instead.

**This run is a 24-HOUR CANARY with pre-registered acceptance criteria.** It stops itself cleanly at the deadline (the launcher refuses to spawn past it, so the last segment ends at its own rollover) and aborts early on: breaker trip, two consecutive segments with no section shipped, a rotation loop (>1 rotation per section), or an unexplained gate refusal. The criteria it is being judged against are recorded in [`docs/overnight/run-log.md`](../../docs/overnight/run-log.md) and must be judged on evidence, not impression.

## 2. `read_cache_block` counts a SUBAGENT's reads as the main session's, so the first main-session read of any surface a mapper touched is blocked twice

      Observed live 2026-08-01 03:26-03:31 on TODO-04 section 45. A `section-context-mapper` dispatch read the harness script and `docs/testing/usermode-output-formats.md`; the mapper's context was then discarded, as designed.       - **The hook's own message names this case as exempt** -- "Legitimate re-reads are NOT gated and need no action from you: ... inside a subagent" -- so the intent is already correct and the defect is purely in attribution: the counter is keyed per run/session, not per context, and a subagent's Read events increment the main session's tally.

## 7. `read_cache_block` charges SUBAGENT reads to the main session, blocking it on content it never received

- [ ] Scope the read ledger to the context that actually holds the bytes
      Observed twice on 2026-08-01, 17:55 and 18:05, both on `src/kernel/test/test_usermode.c` lines 1690-1849. A `kernel-explorer` dispatch read that range in its own throwaway context; when the MAIN session then read it for the first time, the hook BLOCKED with "ALREADY in this session's context -- read #12, 4m ago" and told me to scroll up and reuse a copy that does not exist here.
      - The subagent's whole purpose is that its reads do NOT enter this context -- that is the offload doctrine's premise. Charging them to the main session's ledger inverts it: the more legwork is correctly delegated, the more the main session is refused its own first read.
      - **Cost per occurrence is two tool calls** (blocked attempt, then the deliberate repeat that the 2-of-2 limit releases) plus the reasoning to decide the block was wrong -- which is the expensive part, because the honest default is to trust the hook.
      - It is self-clearing rather than wedging, so it reads as noise; the risk is the opposite failure, where an agent believes the message and proceeds on content it never read.
      - **Shape of the fix:** record the reader's context id with each ledger entry and only count entries from the current one, or simply do not record reads made inside a subagent.

## 10a. `run-artifact.sh` reports `errors: 8` on a green build, because `-Werror` is in every compile command line

- [ ] Extract errors from diagnostic lines, not from any line containing the substring `error`
      Observed 2026-08-02 03:52 on TODO-04 section 53. `run-artifact.sh s53-build2 -- bash scripts/build.sh` returned `{"exit": 0, ..., "errors": 8}` while `tail -1 build/build.log` said `=== BUILD OK ===`. Every one of the eight was a compiler INVOCATION line carrying `-Werror` in its flags, plus the `ld.lld` link line.
      - **Why it costs more than a wrong number:** the envelope exists so the model does not read the log, and a nonzero `errors` on a green build is precisely the signal that makes it read the log anyway. Confirming these eight were noise meant grepping the artifact and pulling a single ~40 KB link command line into context -- the exact flood the wrapper was built to prevent, caused by the wrapper's own summary.
      - **Mechanism:** the extractor matches `error` case-insensitively anywhere in a line. `-Werror` appears in every kernel and user compile command, so the count scales with how many files the incremental build happened to touch (8 here; a clean build would report hundreds).
      - **Shape of the fix:** match the compiler's diagnostic grammar (`<file>:<line>:<col>: error:`) and the linker's (`ld.lld: error:`), or simply ignore any line beginning with a compiler/linker executable name. Cheaper still: when `exit == 0`, report `errors: 0` and keep the extracted lines under a separate key.

      - **Measured cost, this section alone:** the loop form was abandoned and replaced by ten separate single-run tool calls, and a validation test of a new `TEST_MEM` knob could not be run through the wrapper at all -- it was verified by re-implementing the validation logic inline in `bash -c` instead, which is strictly worse evidence than running the real script.

      - **Shape C, trailing redirect then `;` chain.** Observed 2026-08-02 06:5x on TODO-04 section 54. `bash scripts/overnight/run-artifact.sh s54-build3 -- bash scripts/build.sh >/dev/null 2>&1; tail -1 build/build.log; grep -m6 "error:" build/build.log` was BLOCKed with `matched segment: bash scripts/build.sh`, while the byte-identical command WITHOUT the trailing `>/dev/null 2>&1;` chain had been allowed twice minutes earlier. So the wrapper credit survives a bare wrapper call but not a redirect plus a `;`-joined tail, which is the ordinary shape for "run it quietly, then quote the receipt myself" -- the exact behaviour the gate's own message asks for ("you quote the tail yourself"). Cost here was one wasted turn and a re-issue as two separate tool calls.

## 11. A section shipped, reviewed and run-logged with its Implementation Order row never flipped, so the oracle re-opened a finished section

- [ ] Make the ship boundary fail closed on a section whose body is stamped but whose IO-table row is still `[ ]`
      Observed 2026-08-02 08:3x, first action of the session that resumed after TODO-04 section 54's rollover. `advance-work.py` returned `next_section: {n: 54, class: NEEDS_WORK}` with `open_items: 0`, and `sequencer_triage.py --classify` agreed -- while section 54's body carried all three items `[x]`, a `**Verified:** 2026-08-02 | commit 358f6183` stamp and a `**Quality reviewed:** ... 7H+6M+4L fixed, 0 open` stamp, and the three commits `358f6183` (ship), `009c7117` (review) and `387c01b8` (run log) were all on `main`.

The triage oracle classes a section from its Implementation Order row plus stamps and never reads the body, so a stamped-but-unflipped row is indistinguishable from unstarted work. The ship commit `358f6183` touched the TODO (12 lines) and the review commit `009c7117` touched it again (8 lines) -- both edited the body, neither flipped the row.
      - **Cost if undetected:** the next worker re-implements a finished section from a `section_pack` that lists zero open items. Here it cost one orientation turn plus a repair commit; unnoticed it would have cost a full section pipeline (design + adversarial + consistency + perf Codex) against work already done.
      - **Why the existing nets missed it:** `review-todo-section`'s PreToolUse gate keys on a commit that FLIPS `| [x] |` without a `**Verified:**` stamp -- the inverse of this defect, so an unflipped row trips nothing. `rollover` checks tree/push/receipt state, not TODO-body-vs-row agreement, so the section rolled over VERIFIED with the inconsistency in place.
      - **Shape of the fix:** a cheap consistency check comparing each `## N.` section's stamp state against its IO-table row status, run where it can fail closed -- the `rollover` gate is the natural point (it already rebuilds the todo-graph), and `scripts/lint.sh` is the cheaper always-on home. A section carrying both stamps whose row is not `[x]` (or a row `[x]` whose body has open `[ ]` items) is an ERROR, not a warning.

- [x] ROOT CAUSE of both index sweeps: the post-commit COUNT refresh amends with a BARE `--amend`, silently converting every path-limited commit in the repo into a full-index commit
      Found 2026-08-02 10:00 after a THIRD sweep, and it retires two earlier misdiagnoses. `.githooks/post-commit:345` ran `git add COUNT.md README.md` then `git commit --amend --no-edit --no-verify`. A bare `--amend` commits the WHOLE INDEX, so `git commit -- <paths>` -- the documented protection for working alongside a live run -- was undone microseconds after it worked.
      - **Measured three times, each mistaken for something else.** 2026-07-31: an attended commit that staged only its own four files still shipped the run's staged section deferral (8 lines), attributed to "the index is shared". 2026-08-02 09:53: a path-limited THREE-path commit shipped **13 files, including 527 lines of the run's in-flight `test_usermode_launcher.c`** under the message "todo: cap section growth at 40/60". The 2026-07-28 live-gotcha about the RUN sweeping an operator's `token-saver-v03.md` is very likely the same mechanism seen from the other side.
      - **Why it hid so well.** The commit SUCCEEDS and its message, paths and diff all look correct at the moment of authoring; the widening happens in the post-commit hook, after any output a human reads. Regression `test_post_commit_amend_scope.py` drives a real repo where a second session has staged work, commits path-limited, runs the hook, and asserts the other session's file is NEITHER in the commit NOR removed from the index. MUTATION-TESTED: restoring the bare amend fails it with the exact observed symptom.

The mitigation was never the weak point; the hook was. Attended repair alongside a live run is now actually safe rather than nominally safe -- which matters more for the worktree split than any of the guards, because it is the failure that kept happening despite them.
