## TODO-01 — Disk Image, USB & Release Artifacts 🆕 NEW

Create `todo/12-installer-release/TODO-01-release-artifacts.md`. The OS builds a raw GPT disk image and a bootable ISO; this TODO adds the release artifact pipeline that turns those into versioned, signed, distributable deliverables ready for end users — the difference between a development build and a product release. Sections: (1) versioning scheme — adopt `MAJOR.MINOR.BUILD` (e.g., `1.0.22000`); `BUILD` = sequential CI build number; version baked into `HKLM\SYSTEM\Version` at build time via `scripts/set-version.sh`; `include/kernel/version.h` auto-generated (`#define OS_VERSION_MAJOR`, `MINOR`, `BUILD`, `OS_VERSION_STRING "Impossible OS 1.0 (Build 22000)"`); kernel boot log prints version string; `winver.exe` displays it; (2) GPT disk image — `scripts/build.sh` already produces `build/system-disk.img`; add `scripts/release-image.sh` that stamps version into image, runs a post-build integrity check (scan EFI partition for `BOOTX64.EFI` presence, scan IXFS partition for `kernel.exe`), compresses with `zstd -T0 -9` to `build/impossible-os-{version}.img.zst`; SHA-256 alongside: `build/impossible-os-{version}.img.zst.sha256`; (3) USB-bootable image — `scripts/make-usb.sh <device>` writes raw disk image to USB with `dd bs=4M conv=fsync`; verify: re-read first 512 bytes of USB, compare to image MBR/GPT signature; interactive confirmation "Write to /dev/sdX? All data will be erased. [yes/no]"; also produce a self-contained USB creator app for Windows: `tools/usb-creator/usb_creator.c` (host-side, GCC) that lists removable drives and wraps `dd` or Win32 `DeviceIoControl`; (4) bootable ISO — `scripts/make-iso.sh` (→ XREF `09-services-security/TODO-11 §1`) produces `build/impossible-os-{version}.iso`; add Joliet + Rock Ridge extensions to `xorriso` call so ISO is readable on Windows and macOS hosts; include `README.txt` at ISO root: installation instructions, minimum hardware; SHA-256 alongside; verify: `file build/*.iso` must show `ISO 9660 CD-ROM`; (5) code signing — `scripts/sign-release.sh`: use `cng_sign` (→ XREF `08-desktop-shell/TODO-07 §7`) to sign `kernel.exe` and `BOOTX64.EFI` with the project's Ed25519 private key (stored as GitHub Actions secret); embed signature in PE/ELF section; on boot: bootloader optionally verifies kernel signature (controlled by `HKLM\SYSTEM\SecureBoot\Enforce` = 0 by default, 1 for production); also sign `impossible-os-{version}.iso` and `.img.zst` with GPG for release integrity; (6) artifact manifest — `build/release-{version}.json`: JSON file listing all artifacts with filename, size_bytes, sha256, build_time, git_commit, os_version; auto-generated by `scripts/make-manifest.sh`; consumers (the update check API from `09-services-security/TODO-03`) parse this to find download URLs and verify downloads; (7) VM image variants — `scripts/make-vm-images.sh`: `qemu-img convert -O vmdk build/system-disk.img build/impossible-os-{version}.vmdk` (VirtualBox/VMware); `qemu-img convert -O vpc build/system-disk.img build/impossible-os-{version}.vhd` (Hyper-V legacy); `qemu-img convert -O vhdx` (Hyper-V modern); each with SHA-256; include `.ovf` descriptor for VirtualBox import (4 GB RAM, 2 vCPU, EFI firmware, Secure Boot disabled); (8) reproducible builds — all build scripts set `SOURCE_DATE_EPOCH` from latest git commit timestamp; `BUILD_TIMESTAMP` in `version.h` fixed to epoch; binary should be byte-for-byte reproducible given same toolchain; document in `docs/infrastructure/reproducible-builds.md`; add `make verify-reproducible` target.

## TODO-02 — Unattended Installation & Deployment 🆕 NEW

Create `todo/12-installer-release/TODO-02-unattended-install.md`. The interactive installer wizard is done (→ XREF `09-services-security/TODO-11`); this TODO adds unattended installation (answer files), OEM preload support, and enterprise imaging — the deployment scenarios needed for automated VM provisioning, CI/CD, and hardware partner customization. Sections: (1) answer file format — `answer.ini` INI format at root of installation media or passed via kernel cmdline `answer=<path>`; sections: `[Setup]` (Language, Timezone, KeyboardLayout, InstallMode: Auto/Interactive), `[Disk]` (DiskIndex, PartitionScheme: GPT, EFISize: 512, SystemFS: IXFS/NTFS), `[User]` (Username, PasswordHash [Argon2i hex], Privilege: Admin/User, AutoLogin: 0/1), `[Network]` (DHCP: 1, StaticIP, Gateway, DNS), `[OEM]` (CompanyName, SupportURL, WallpaperPath, DefaultApps), `[Packages]` (InstallList: comma-separated .ipkg URLs or local paths); (2) unattended install mode — installer checks for answer file at boot: `\answer.ini` on installation media, or `HKLM\SYSTEM\UnattendedSetup\AnswerFile` Registry key; if found: skip all UI dialogs, proceed directly through partitioning, format, copy, user creation, first-boot registration using answer file values; log all decisions to `C:\Impossible\System\Logs\setup.log`; on completion: auto-restart without user interaction; `[Setup] InstallMode=Interactive` forces wizard even if answer file present; (3) `sysprep` — `sysprep.exe /generalize /oobe /shutdown`: clear machine-specific data (SID, hostname, hardware fingerprint, network adapter GUIDs, cached credentials); set `HKLM\SYSTEM\FirstBoot = 1` to trigger OOBE wizard on next boot; seal the installation for duplication; `sysprep /audit` boots directly to admin session for driver installation before sealing; used for: OEM imaging, VM template creation, CI snapshot base; `sysprep.cpl` Control Panel entry; (4) OEM customization — answer file `[OEM]` section allows hardware partners to: set default wallpaper (path copied from media to `C:\Impossible\Web\Wallpaper\oem-default.jpg`), set OEM company name (shown in System Properties), set support URL, pre-install apps from IPKG packages, include custom drivers (`.kmod` files in `\$OEM$\Drivers\` on media → auto-loaded by installer), inject Registry tweaks from `\$OEM$\$1\registry.reg` file; OEM info stored in `HKLM\SYSTEM\OEM\{Name, SupportURL, Logo}`; (5) WIM/image capture — `imagex.exe /capture C:\ C:\Impossible.wim "Impossible OS" /compress fast`: capture IXFS partition to WIM format (Windows Imaging Format compatible, or custom .iim variant); WIM is a single-instanced file archive format — identical files stored once; `imagex /apply` extracts WIM to target partition; enables: department-specific images with pre-installed apps, rapid bare-metal recovery, CI/CD golden images; `DISM`-style command (stretch): `dism /get-imageinfo`, `/add-package`, `/remove-feature`; (6) network boot (PXE) — minimal PXE server in `src/apps/pxeserver/pxeserver.c`: DHCP proxy (intercepts PXE boot requests), TFTP server (serves `BOOTX64.EFI` + `kernel.exe` + `answer.ini`); boot sequence: NIC PXE ROM → DHCP → TFTP gets EFI → UEFI loads kernel → installer runs in unattended mode; used for: fleet deployment without USB media, CI/CD bare-metal testing; configure TFTP root from Registry; `pxesrv start/stop/status` shell command; (7) VM provisioning templates — `scripts/provision-qemu.sh <answer.ini>`: creates new QCOW2 disk, boots ISO with answer file via `-kernel`/`-initrd` or by appending `answer=` to kernel cmdline; waits for power-off signal, then QCOW2 is ready as provisioned VM; `scripts/provision-hyperv.ps1`: PowerShell equivalent for Hyper-V on Windows host; used by CI to spin up fresh VMs for regression testing; (8) enterprise deployment guide — `docs/guides/enterprise-deployment.md`: walkthrough of answer-file creation, sysprep, WIM capture, PXE boot, and mass deployment; includes worked examples for: QEMU farm, Hyper-V cluster, bare-metal lab; document all answer file keys with descriptions and defaults; document OEM customization hooks.

## TODO-03 — Update Server Infrastructure 🆕 NEW

Create `todo/12-installer-release/TODO-03-update-server.md`. The OS-side update client is done (→ XREF `09-services-security/TODO-03`); this TODO builds the server infrastructure that delivers updates — the version manifest API, IPKG package repository, CDN strategy, and release promotion pipeline. Sections: (1) version manifest API — `GET https://impossible-os.dev/api/version?channel=stable` returns JSON: `{"version":"1.0.22100","url":"https://cdn.impossible-os.dev/releases/stable/impossible-os-1.0.22100.img.zst","sha256":"...","size":524288000,"type":"MINOR","changelog_url":"https://impossible-os.dev/changelog/1.0.22100","min_version":"1.0.21000"}`; channels: `stable`, `beta`, `dev`; served from a static JSON file (no database needed initially, updated by CI on each release); `GET /api/changelog/{version}` returns Markdown changelog; SSL via Let's Encrypt; (2) IPKG package repository — `GET https://pkg.impossible-os.dev/index.json` returns array of `{"name","version","description","category","size","sha256","url","dependencies":[]}`; packages are `.ipkg` files hosted in `packages/` directory; `ipkg install <name>` fetches from repository index, downloads, verifies SHA-256, runs installer; `ipkg search <query>` filters index by name/description; `ipkg list` shows installed packages from `HKLM\SOFTWARE\Installed\`; `ipkg update` refreshes index cache; `ipkg upgrade` upgrades all installed packages; `HKCU\Software\Impossible\PackageManager\RepoURL` (default `https://pkg.impossible-os.dev/`); (3) package submission — `ipkg submit <package.ipkg>` or GitHub PR to `rizonesoft/impossible-os-packages` repo; CI runs: signature check, malware scan stub, install/uninstall test in QEMU sandbox, manifest validation; approved packages land in the repo index within 24 h; maintainer tools: `ipkg-sign <package.ipkg> <key>`, `ipkg-verify <package.ipkg>`; package categories: System Tools, Development, Multimedia, Internet, Productivity, Games; (4) CDN & hosting — GitHub Releases hosts the disk image + ISO artifacts (up to 2 GB per file); Cloudflare R2 (free tier) stores IPKG packages; `scripts/upload-release.sh`: uses `gh release create` + `gh release upload` for artifacts on GitHub Releases; R2 upload via `rclone` or Cloudflare Workers API for packages; CDN URL format: `https://cdn.impossible-os.dev/{channel}/{artifact}`; update API hosted as GitHub Pages static site with JSON files (free, versioned by git); (5) release promotion pipeline — build → `dev` channel (every CI green build), → `beta` channel (manual trigger, release candidate), → `stable` channel (manual approval + sign-off checklist); promotion script: `scripts/promote-release.sh <version> <from-channel> <to-channel>` updates the channel JSON manifests and tags the Git commit; rollback: `scripts/rollback-release.sh <channel> <previous-version>` reverts channel JSON; (6) update delta packages — for MINOR updates: `scripts/make-delta.sh <old-version> <new-version>` diffs the two disk images and creates a delta `.ipkg` containing only changed files; delta packages are 10–50× smaller than full updates; update client checks for delta first, falls back to full if delta unavailable; delta format: ZIP of modified files + `delta.ini` (old version, new version, file list with hashes); (7) telemetry pipeline (opt-in) — on-OS telemetry client (→ XREF `09-services-security/TODO-12 §9`) sends anonymous events to `https://telemetry.impossible-os.dev/`; event format: `{"os_version","build","event_type","timestamp"}`; no PII; server: Cloudflare Worker → D1 (SQLite) → Grafana dashboard; visible at `https://stats.impossible-os.dev/` (public); opt-out via `HKLM\SYSTEM\Telemetry\Enabled = 0`; GDPR compliant (EU users auto-opt-out by IP region); (8) status page — `https://status.impossible-os.dev/`: shows update server health, package repo availability, CDN status; auto-updated by GitHub Actions health checks every 5 min; incident history; email/webhook notification for maintainers on outage.

## TODO-04 — Release QA & Platform Certification 🆕 NEW

Create `todo/12-installer-release/TODO-04-release-qa.md`. The OS is feature-complete; before a public release, a structured QA process ensures stability, performance parity with Windows 11/Linux, and correct behavior across all supported platforms. Sections: (1) automated regression test suite — `scripts/run-tests.sh`: boot OS in QEMU headless mode with `-nographic -serial stdio`; parse serial output for `[OK]`/`[FAIL]` lines from kernel boot + subsystem init; test matrix: kernel init sequence, memory allocator (alloc/free 1000× loop), filesystem CRUD (create/read/write/delete 100 files), registry read/write/delete, networking (DHCP lease, DNS resolve google.com, HTTP GET), desktop compositor (render 100 frames, measure FPS via PIT), process creation (spawn/exit 50 processes); each test emits structured output: `TEST <name> PASS|FAIL [duration_ms]`; CI fails the build if any test fails; (2) QEMU validation — `scripts/qemu-test.sh`: boot with `bash scripts/build.sh run`, wait for serial `[READY]` marker, run automated test sequence via serial input, capture all serial output to `build/qemu-test.log`, grep for failures; test scenarios: cold boot, warm reboot, ACPI shutdown, hibernate/resume (stretch), memory pressure (allocate 90% RAM), disk stress (write 100 MB file), network throughput (loopback socket ping-pong); must all pass before release tag; (3) Hyper-V certification — `scripts/hyperv-test.ps1` (Windows host); creates Gen2 VM (2 GB RAM, 2 vCPU, 40 GB VHDX, Secure Boot off, UEFI); boots from ISO; installs to VHDX via unattended answer file; reboots from VHDX; verifies 8 required tests (→ XREF `09-services-security/TODO-11 §8`); additional: test all keyboard keys via PS/2 emulation, test mouse integration, test clipboard via Hyper-V VMBus, test screen resize; documents any Hyper-V-specific bugs in `docs/guides/hyperv-known-issues.md`; (4) VirtualBox certification — `scripts/vbox-test.sh`: create VirtualBox VM (EFI, 2 GB RAM, 40 GB VDI, Bridged networking); boot from OVF import; run test suite; additional VirtualBox-specific tests: VirtualBox Guest Additions detection (→ XREF `04-drivers-hardware` guest additions), shared clipboard, shared folders, drag-and-drop; known VirtualBox quirks documented; (5) real hardware checklist — `docs/guides/hardware-test-checklist.md`: structured checklist for human testers on physical hardware; sections: UEFI boot (Secure Boot off), display (GOP framebuffer at native resolution), keyboard (PS/2 + USB HID), mouse (PS/2 + USB HID), storage (AHCI SSD + NVMe SSD), networking (Realtek RTL8111 + Intel I219), audio (HD Audio), USB (USB 2.0 + 3.0 hubs, flash drives), ACPI shutdown/reboot/sleep; results table: hardware model, tested, pass/fail, notes; target: tested on ≥ 3 distinct physical machines before stable release; (6) performance benchmarks — `scripts/benchmark.sh`: automated performance tests run in QEMU and logged to `build/benchmark-{version}.json`; metrics: boot time (UEFI handoff → desktop [READY] marker, target < 5 s in QEMU), memory allocator throughput (alloc+free pairs per second, target > 1M/s), filesystem sequential write (bytes/s, target > 500 MB/s on VirtIO), network TCP throughput (loopback, target > 1 Gbps), frame render time (compositor, target < 16 ms = 60 FPS), process spawn latency (target < 1 ms); compare against baseline from previous release (flag regressions > 10%); stretch: compare metrics against Linux kernel boot time and Windows 11 boot time (documented, not automated); (7) release readiness checklist — `docs/guides/release-checklist.md`: gated sign-off list before tagging stable release; items: `[ ]` all CI tests pass, `[ ]` QEMU validation pass, `[ ]` Hyper-V certification pass, `[ ]` VirtualBox certification pass, `[ ]` no P0 open bugs, `[ ]` performance benchmarks not regressed, `[ ]` version number bumped, `[ ]` changelog written, `[ ]` disk image signed, `[ ]` SDK version synchronized, `[ ]` release notes reviewed; PR to `main` with checklist filled in required before merge to release branch; (8) crash analytics review — before each release: review crash dumps from `C:\Impossible\System\CrashDumps\` collected during testing; triage all unresolved panics; add kernel assertions that catch the conditions that led to resolved crashes; run ASAN-equivalent (stack guard pages, PMM sentinel pages) during QA builds to catch memory errors early; goal: 0 kernel panics during 30-minute QEMU soak test.
