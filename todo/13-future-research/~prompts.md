## TODO-01 — ARM64 & RISC-V Architecture Port 🆕 NEW

Create `todo/13-future-research/TODO-01-multi-arch-port.md`. The OS targets x86-64 exclusively; an ARM64 port opens the door to Apple Silicon Macs, Qualcomm Snapdragon laptops, Raspberry Pi, and cloud VMs — the most strategically valuable architectures outside x86-64. This is a research spike to scope the effort before committing to implementation. Sections: (1) ARM64 (AArch64) architecture gap analysis — audit every x86-64-specific construct in the codebase: inline assembly (`__asm__`), MSR reads/writes (LSTAR, STAR, SFMASK), `RDRAND`, CPUID, APIC MMIO, HPET/TSC timing, `WRMSR`/`RDMSR`, `cli`/`sti`, `hlt`, `iretq`, `sysret`; document each in a spreadsheet (file + line + ARM64 equivalent); estimate LOC delta to port; target: < 5% of total codebase is arch-specific; (2) AArch64 boot path — UEFI on ARM64 is identical protocol to x86 (same `.efi` binary format via AArch64 ELF → PE); the bootloader is already PE/COFF so the UEFI protocol layer ports cleanly; key differences: no GDT/IDT (ARM64 uses vector table at VBAR_EL1), exception levels (EL0=user, EL1=kernel, EL2=hypervisor, EL3=secure), `mrs`/`msr` for system registers, `svc #0` syscall instead of `syscall`, page sizes 4K/16K/64K; research: write a minimal AArch64 kernel that prints via UART (MMIO PL011) and boots under QEMU `virt` machine; (3) AArch64 port plan — layer the port: (A) bootloader: compile `bootx64.c` for AArch64 target (single conditional `#ifdef ARCH_ARM64` block), same UEFI GOP + ELF loader; (B) arch-specific layer `src/arch/arm64/` with: GIC (Generic Interrupt Controller) instead of APIC, PSCI (Power State Coordination Interface) for SMP bringup, ARM64 page table format (4-level, identical concept to x86 but different bit layout), `arch_cpu_relax()`, `arch_yield()`; (C) kernel core: refactor `#ifdef ARCH_X86_64` / `ARCH_ARM64` guards throughout sched, mm, ipc; (D) compiler: `clang-19 --target=aarch64-elf` already works; (4) RISC-V (RV64GC) gap analysis — RISC-V is the open ISA gaining traction in embedded, RISC-V laptops (StarFive, Milk-V), and datacenter; even simpler than ARM64: M-mode (machine), S-mode (supervisor=kernel), U-mode (user); `ecall` for syscalls; PLIC (Platform-Level Interrupt Controller); SBI (Supervisor Binary Interface) replaces PSCI; no UEFI required (U-Boot + OpenSBI boot chain); key challenge: QEMU `virt` machine well-supported; UEFI on RISC-V via TianoCore EDK2 also possible; (5) build system multi-arch — `scripts/build.sh ARCH=arm64` or `ARCH=riscv64`; cross-compile with `clang-19 --target=aarch64-elf` or `--target=riscv64-elf`; arch-specific linker scripts; arch-specific output binary name (`kernel-arm64.elf`); QEMU invocations: `qemu-system-aarch64 -machine virt -cpu cortex-a72`, `qemu-system-riscv64 -machine virt -cpu rv64`; CI matrix: build for all three architectures on every push (compile-only initially, boot test when functional); (6) ABI considerations — Win32 ABI is x86-64 specific (Windows x64 calling convention: RCX, RDX, R8, R9); on ARM64, Windows uses AAPCS64 (args in X0-X7); Win32 API headers need conditional ABI macros; `__attribute__((ms_abi))` for x86-64, native AAPCS64 on ARM64; most kernel-internal code is ABI-neutral already; user-mode ARM64 PE binaries use Microsoft ARM64 ABI (same as Windows 11 ARM); (7) research deliverables — produce `docs/architecture/multi-arch-port-plan.md` with: effort estimate (person-months), dependency tree, arch-specific file inventory, recommended port order (ARM64 first, RISC-V second), QEMU test strategy, blocking issues; no code changes in the kernel during the research phase — output is the plan document only.

## TODO-02 — Type-1 Hypervisor (ImpossibleHV) 🆕 NEW

Create `todo/13-future-research/TODO-02-hypervisor.md`. A built-in Type-1 hypervisor lets Impossible OS run Windows, Linux, and other OSes as guests — the feature that transforms it from an OS into a platform. This spike researches feasibility and defines the minimal viable hypervisor design. Sections: (1) Intel VT-x/AMD-V gap analysis — read Intel SDM Vol. 3C (VMX) and AMD APM Vol. 2 (SVM); key concepts: VMX root/non-root modes (host/guest), VMCS (VM Control Structure, 4 KB per vCPU), VM entry/exit, EPT (Extended Page Tables = nested paging), VPID (TLB tagging), I/O bitmaps, MSR bitmaps, APIC virtualization; check CPU support: `cpuid.ecx.VMXE` (bit 5) for Intel, `cpuid.ecx.SVM` (bit 2) for AMD; enable VMX: `CR4.VMXE = 1`, `VMXON region` (4 KB), `VMXON` instruction; (2) minimal hypervisor design — Type-1.5 (hosted): Impossible OS kernel runs at VMX root, guests run at VMX non-root; no separate hypervisor binary; kernel becomes the VMM (Virtual Machine Monitor); minimal VMCS configuration: guest state (RIP, RSP, CS, SS, CR0, CR3, CR4, EFER, RFLAGS), host state (mirror of kernel registers), control fields (I/O bitmap = all exits, EPT pointer, VPID=1); VM entry: `VMLAUNCH`/`VMRESUME`; VM exit handlers: I/O port access, CPUID, RDMSR/WRMSR, EPT violation, HLT, XSETBV; (3) minimal Linux guest proof-of-concept — boot a micro-Linux image (busybox initrd, ~10 MB) as a VM guest: allocate 128 MB guest physical memory from PMM, set up EPT mapping, load Linux `bzImage` into guest memory at 0x100000, set VMCS guest state to Linux boot protocol (BX=0, BP=0, SI=pointer to `boot_params`), VMLAUNCH; handle I/O exits for COM1 serial (port 0x3F8) → forward to kernel serial log; handle HLT → pause vCPU; measure: time from VMLAUNCH to Linux `[OK]` first line on serial; (4) virtio device emulation — guests need virtual devices; implement minimal `virtio-blk` and `virtio-net` device emulation in the VMM: virtio MMIO transport (guest reads/writes MMIO → VM exit → VMM handles); virtio queue processing (split-ring: available ring → VMM processes → used ring); `virtio-blk`: map guest block I/O requests to host filesystem files (`.img` disk images); `virtio-net`: forward guest packets through host network stack; (5) snapshot & live migration research — VM snapshot: pause vCPU, serialize VMCS + guest memory (via PMM page list) to a file, resume; live migration: copy guest memory pages to destination while running (dirty page tracking via EPT write bits), pause briefly to copy final dirty pages, resume on destination; requires distributed kernel support (TODO-07); research: read KVM source for snapshot format reference; (6) GPU passthrough research — SR-IOV or VFIO-style GPU passthrough: assign a physical GPU's PCI BAR directly to a guest VM (no emulation overhead); requires IOMMU (Intel VT-d or AMD-Vi) to isolate DMA; `IOMMU_MAP(pci_device, guest_physical)` maps device to guest; complex prerequisites: PCIe hot-plug, IOMMU driver; document feasibility and blocking dependencies; (7) research deliverables — `docs/architecture/hypervisor-design.md`: CPU feature requirements, VMCS field layout, device emulation plan, guest OS support matrix (Linux x64, Windows 10 x64, ImpossibleOS), effort estimate, phased implementation plan (Phase 1: single vCPU Linux boot, Phase 2: multi-vCPU, Phase 3: virtio devices, Phase 4: snapshots); prototype code (non-production) in `src/kernel/hypervisor/` gated by `#ifdef ENABLE_HYPERVISOR`.

## TODO-04 — Secure Boot, TPM 2.0 & Measured Boot 🆕 NEW

Create `todo/13-future-research/TODO-04-secureboot-tpm.md`. This spike covers UEFI Secure Boot enforcement, TPM 2.0 integration for attestation and full-disk encryption, and the measured boot chain — the security hardening needed for enterprise and cloud deployment scenarios. Sections: (1) UEFI Secure Boot implementation — Secure Boot requires signing `BOOTX64.EFI` with a key in the firmware's `db` (allowed signatures database); current status: Secure Boot is disabled in test VMs; production path: generate a self-signed Platform Key (PK) + Key Exchange Key (KEK) + database key (db); sign `BOOTX64.EFI` with `sbsign` tool; enroll PK/KEK/db into UEFI NVRAM via `KeyEnroll` protocol; bootloader verifies kernel signature via UEFI `SECURITY_PROTOCOL`; extend to kernel: `BOOTX64.EFI` verifies `kernel.exe` signature before loading; chain of trust: UEFI firmware → `BOOTX64.EFI` → `kernel.exe` → drivers; `HKLM\SYSTEM\SecureBoot\Enforce` controls kernel-level enforcement; (2) TPM 2.0 driver — TPM 2.0 is accessible via `CRB` (Command-Response Buffer) or `FIFO` interfaces at MMIO (ACPI `\\_SB.TPM` device); commands sent as binary blobs (TPM2 spec Part 3); implement: `tpm2_startup(TPM2_SU_CLEAR)`, `tpm2_selftest()`, `tpm2_get_random(buf, len)` (hardware RNG), `tpm2_pcr_read(pcr_index)` (Platform Configuration Register), `tpm2_pcr_extend(index, digest)` (extend PCR with SHA-256); integrate CSPRNG: feed TPM RNG into kernel entropy pool (→ XREF `11-user-platform-sdk/TODO-01 §4`); QEMU supports TPM emulation: `-tpmdev passthrough,id=tpm0,path=/dev/tpm0` or `libtpms`; (3) measured boot chain — PCR 0–7 are extended by UEFI firmware with hashes of each boot component; extend this chain: PCR 8 = `kernel.exe` hash (extended by bootloader before jumping), PCR 9 = kernel module hashes (extended before each `kmod_load`), PCR 10 = first-user-process hash; after boot: `tpm2_pcr_read()` shows full chain; TPM Quote: `tpm2_quote(PCR_mask, nonce)` signs PCR values with TPM key → remote attestation proof; store expected PCR values in `HKLM\SYSTEM\SecureBoot\ExpectedPCRs` for local attestation check; (4) BitLocker-equivalent full disk encryption — FDE research: encrypt IXFS partition at block layer using AES-256-XTS (XTS-AES mode, standard for disk encryption); `volume_key` (256-bit) derived from TPM2 sealed blob (`tpm2_create` under PCR policy → only unseals if boot PCR values match); boot flow: bootloader reads sealed blob from TPM → PCR policy check → unseal volume key → pass to kernel → kernel decrypts IXFS blocks transparently; key backup: encrypt `volume_key` with user password (Argon2id KDF) → store in `HKLM\SYSTEM\FDE\RecoveryKey`; `bitlocker.cpl` Control Panel applet (Enable FDE, Backup recovery key, Suspend); (5) vTPM for VMs — for guest VMs running in ImpossibleHV (TODO-02): emulate a virtual TPM per VM; `vtpm_create_vm(vm_id)` allocates per-VM TPM state; forward `tpm2_*` commands from guest to `libtpms` (software TPM emulator); each VM gets independent PCR hierarchy and sealed key material; enables running FDE inside VMs; (6) research deliverables — `docs/architecture/secure-boot-tpm-plan.md`: Secure Boot key hierarchy diagram, TPM 2.0 command table (which commands needed + byte-level encoding), measured boot PCR assignment table, FDE architecture diagram, blocking dependencies (ACPI TPM device enumeration), effort estimate; prototype: TPM RNG working in QEMU with `swtpm` before any production code.

## TODO-06 — Distributed OS & Cluster Features 🆕 NEW

Create `todo/13-future-research/TODO-06-distributed-os.md`. A single-node OS is table stakes; this spike explores the distributed features that would make Impossible OS genuinely novel — transparent process migration, distributed shared memory, a cluster filesystem, and a peer-to-peer update mesh. Prerequisites: full networking stack, IPC, and hypervisor (TODO-02). Sections: (1) distributed process model — research: Sprite OS (1987), Amoeba OS, Plan 9 from Bell Labs; key idea: processes are location-transparent — a process on node A can transparently communicate with a process on node B using the same IPC primitives as intra-node; implementation path: extend `pipe_send`/`pipe_recv` to handle remote endpoints via TCP tunneling; `struct ipc_endpoint` adds `remote_ip` + `remote_port` field; kernel routes local endpoints through existing IPC, remote endpoints through TCP; `SYS_ENDPOINT_BIND(address)` allows processes to publish endpoints under cluster-wide names; (2) transparent process migration — pause a process on node A: save all state (registers, memory pages via VMM dump, open file descriptors, socket states), transmit over TCP, resume on node B; challenges: open sockets must be re-homed (TCP connection migration via MPTCP or proxy), mapped files must be accessible from node B (requires distributed filesystem), kernel modules hosting process state must be present on node B; research: read CRIU (Checkpoint/Restore In Userspace) design; prototype: migrate a stateless process (no open files or sockets) between two QEMU instances; (3) distributed filesystem (ImpossibleFS/DFS) — a cluster-visible filesystem layer above the local VFS; `dfs_mount(peer_ip)` mounts a remote peer's `C:\` as `\\peer-name\C$` (UNC path); protocol: custom binary RPC over TCP (similar to NFS but simpler); operations: `DFS_READDIR`, `DFS_OPEN`, `DFS_READ`, `DFS_WRITE`, `DFS_STAT`; cache: client-side block cache with cache invalidation on write (similar to NFS v3 weak consistency); RDMA path (stretch): for low-latency inter-node file access over InfiniBand or RoCE; (4) cluster scheduler — extend the kernel scheduler to be cluster-aware: `sched_cluster_submit(task, hint_node)` submits a task to the least-loaded node in the cluster; load balancing via gossip protocol: each node broadcasts CPU/memory utilization every 1 s via UDP multicast; node discovery: multicast group `239.0.0.1:9876`, beacon `{"hostname","ip","cpu_cores","cpu_pct","ram_total","ram_free","os_version"}`; node list maintained in `HKLM\SYSTEM\Cluster\Nodes\{hostname}\{IP,LastSeen,CpuPct,RamFree}`; `cluster status` shell command shows live table; (5) P2P update mesh — instead of central update server (→ XREF `12-installer-release/TODO-03`), nodes share update packages peer-to-peer: BitTorrent-like protocol; node announces its OS version on cluster multicast; peers that already have a newer version offer chunks; reduces central server bandwidth by 90%+ for large deployments; protocol: chunk hash tree (Merkle), piece size 512 KB, peer exchange; `update --p2p` flag enables mesh download mode; (6) research deliverables — `docs/architecture/distributed-os-plan.md`: literature review (Plan 9, Sprite, Amoeba), design principles chosen (which ideas to adopt), IPC extension design (adding remote_ip to endpoints), migration protocol spec, DFS protocol spec, cluster scheduler design, P2P update protocol spec, blocking dependencies, 3-year implementation estimate; prototype goal: two QEMU instances see each other's hostnames via cluster discovery.

## TODO-07 — Formal Verification & Capability Security 🆕 NEW

Create `todo/13-future-research/TODO-07-formal-verification-security.md`. This spike explores two advanced security research directions: formal verification of kernel invariants (proving correctness mathematically) and capability-based security (CHERI-style hardware capabilities replacing pointer-based access control). Both are multi-year research investments that can transform Impossible OS into the most secure consumer OS. Sections: (1) formal verification landscape — survey tools applicable to C kernel code: **Frama-C** (C static analyzer with WP deductive verification plugin, ACSL annotation language); **CBMC** (bounded model checker for C, finds assertion violations up to depth N); **seL4** approach (full functional correctness proof in Isabelle/HOL — 10+ person-years, not realistic to replicate but study the methodology); **TLA+** (temporal logic for protocol specs — excellent for scheduler invariants, IPC deadlock freedom); research goal: identify which kernel subsystem is smallest + highest-risk + most amenable to formal proof; candidates: PMM allocator (simple invariants: every freed page returns to free list), IPC pipe (deadlock freedom), scheduler (priority ordering); (2) PMM verifier prototype — annotate `src/kernel/mm/pmm.c` with Frama-C ACSL contracts: `/*@ requires \valid(frame); ensures pmm_is_allocated(frame); */` on `pmm_alloc_frame()`; `ensures pmm_is_free(frame)` on `pmm_free_frame()`; global invariant: `allocated_count + free_count == total_frames`; run Frama-C WP plugin: `frama-c -wp -wp-rte pmm.c`; resolve all WP goals (likely ~50 goals for PMM); document which goals require manual lemma proofs vs. automatic; result: PMM is provably correct under stated invariants; (3) CHERI capability model research — CHERI (Capability Hardware Enhanced RISC Instructions) adds hardware capabilities to pointers: each pointer carries bounds + permissions + tag bit; tagged memory: 1 tag bit per 16-byte granule prevents capability forgery; capability instructions: `cload`/`cstore` (check capability bounds), `cseal` (seal capability preventing modification), `cunseal`; hardware support: Arm Morello prototype board (4-core Neoverse, CHERI-enabled); RISC-V CHERI extension (research ISA); FPGA emulation via Bluespec; Impossible OS research target: add CHERI-like software capability checks in kernel (no hardware, pure software emulation) as a proof-of-concept; (4) software capability emulation — `capability_t` struct: `{void *base, size_t length, uint32_t permissions, uint32_t tag}`; `cap_check(cap, offset, size, perm)` verifies access at runtime; kernel wraps all user-mode pointer dereferences through `cap_check()`; performance: ~5–10 ns overhead per check (acceptable for syscalls, too slow for hot paths); selective application: apply to syscall argument pointers first (highest attack surface); future: hardware CHERI support eliminates overhead; (5) memory-safe kernel subset — identify which kernel files can be rewritten in a memory-safe language (Zig or Rust) without sacrificing `-ffreestanding` compatibility; Zig: compiles to freestanding bare-metal with `@noreturn`, `@import("builtin")`, linker script control; good candidate for: string functions, JSON parser, registry engine; Rust with `#![no_std]` + custom allocator: good candidate for: network stack, filesystem layer; research: port one 500-LOC kernel file to Zig + verify it integrates cleanly into the build; (6) fuzzing infrastructure — **libFuzzer** / **AFL++** adapted for OS components: build kernel subsystems as userspace-fuzz-targets by mocking kernel APIs (PMM → `malloc`, VFS → in-memory filesystem); fuzz: registry parser (malformed hive files), DNS parser (crafted responses), PE loader (malformed executables), ZIP extractor (crafted ZIP bombs), HTTP parser; `make fuzz-<target>` builds + runs fuzzer; integrate with CI: daily 1-hour fuzz run, fail CI if any crash found; report findings in `docs/security/fuzzing-results.md`; (7) research deliverables — `docs/architecture/formal-verification-plan.md`: tool comparison table, selected subsystem + rationale, Frama-C proof prototype results, ACSL annotation style guide for kernel contributors; `docs/architecture/cheri-capability-plan.md`: CHERI architecture summary, software emulation design, hardware target timeline, integration strategy with existing kernel; `docs/security/capability-threat-model.md`: attack surface analysis showing what CHERI eliminates.

Linux ELF compatibility (→ XREF `09-services-security/TODO-10`) runs statically-linked Linux binaries; this spike explores running macOS Mach-O binaries by implementing a Darwin/XNU subsystem — the most ambitious compatibility layer, enabling access to the macOS software ecosystem. Prerequisites: full NTDLL, Linux compat, and PE loader all stable. Sections: (1) Mach-O binary format — Mach-O uses a different structure from ELF and PE: `mach_header_64` (magic `0xFEEDFACF`, cputype `CPU_TYPE_X86_64`, filetype: `MH_EXECUTE`/`MH_DYLIB`), load commands (`LC_SEGMENT_64`, `LC_DYLD_INFO_ONLY`, `LC_SYMTAB`, `LC_DYSYMTAB`, `LC_MAIN`, `LC_UUID`), segments (`__TEXT`, `__DATA`, `__LINKEDIT`); `macho_load(data, size)`: validate magic, iterate load commands, map `LC_SEGMENT_64` segments to virtual memory, read `LC_MAIN` for entry point; compare complexity to PE loader — Mach-O is similar in concept but different fields; (2) Darwin syscall layer — macOS uses a BSD-derived syscall table (syscall numbers differ from Linux): `write(4)`, `open(5)`, `close(6)`, `read(3)`, `exit(1)`, `mmap(197)`, `munmap(73)`, `getpid(20)`, `fork(2)`, `execve(59)`, `sigaction(46)`, `sigprocmask(48)`; syscall via `syscall` instruction with number in RAX (macOS 64-bit ABI: first arg in RDI, same as SYSV); build a Darwin syscall translation table similar to Linux compat (→ XREF `09-services-security/TODO-10`); path translation: `/Users/{name}/` → `C:\Users\{name}\`; `/Applications/` → `C:\Program Files\`; `/System/Library/` → `C:\Impossible\System\`; (3) dyld (dynamic linker) emulation — macOS programs use `dyld` (dynamic linker daemon) to load `.dylib` shared libraries; `@executable_path/../Frameworks/` relative library paths; `DYLD_LIBRARY_PATH` environment variable; emulate dyld: `dyld_load(mach_o_binary)`: parse `LC_LOAD_DYLIB` commands → load each `.dylib` by path → resolve symbols via `LC_DYLD_INFO_ONLY` bind opcodes; bind opcodes are a compact bytecode for symbol binding (different from PE IAT); (4) Objective-C runtime research — most macOS apps use Objective-C (message-passing OOP): `objc_msgSend(receiver, selector, args...)` dispatches methods; requires `libobjc.dylib` runtime; `GNUstep` (GPL, ~500K LOC) is an open-source Objective-C runtime + Foundation framework; research: can GNUstep be ported to Impossible OS? Dependencies: pthreads (→ kernel threads), Foundation (file I/O, strings, dates), CoreFoundation (property lists, bundles); realistic assessment: statically-linked Objective-C tools (ImageMagick, ffmpeg CLI) might work without Objective-C runtime; (5) CoreFoundation & Foundation stubs — even without full Objective-C, many macOS command-line tools link against `CoreFoundation.framework`; stub the most-called functions: `CFStringCreateWithCString`, `CFRelease`, `CFRetain`, `CFStringGetCStringPtr`, `CFDictionaryCreate`, `CFNumberCreate`, `CFArrayCreate`; map CF types to kernel equivalents; target: statically-linked `curl` and `rsync` macOS binaries run without Objective-C; (6) research deliverables — `docs/architecture/macos-compat-plan.md`: Mach-O format overview, Darwin syscall translation table (first 50 syscalls), dyld emulation design, Objective-C runtime feasibility assessment, target binary classes (CLI tools first, GUI apps never without full AppKit), effort estimate (realistic: 2–3 years for CLI tool support), blocking dependencies; prototype goal: run a statically-compiled macOS `hello` binary that calls `write(4)` syscall on Impossible OS.
