## The one thing that matters

- [x] **DIAGNOSED 2026-07-28: rollover works. The rising `avg context/turn` was LENGTH CONFOUND, and the real finding is that cache-read cost is QUADRATIC in segment length.**
  The original item claimed "rollover is not resetting context". That premise is disproved. Diagnosis ran against the three canary session transcripts themselves (`~/.claude/projects/-home-derickpayne-projects-impossible-os/`: `d865d802`, `3a6a2283`, `e711ac7b`), reading per-message `input + cache_read + cache_creation` rather than the per-segment aggregate the metric reports.

  **Evidence 1: every segment starts at the same context.** Opening context was 59,681 / 57,539 / 57,498 tokens. Rollover resets the worker completely, every time, and the spread across the night is 3.8%. This kills the leading hypothesis outright: the orientation packet (section-pack, brief, cursor state) is NOT growing as the TODO accumulates stamps.
  **Evidence 2: context never falls inside a segment.** Zero drops greater than 50K in any of the three transcripts; growth is strictly monotone for 2.5 hours. Nothing trims, and auto-compaction never fires (peak 580K against a 1M window).
  **Evidence 3: length-matched, the segments are identical.** Truncated to a common 423 assistant messages, mean context was 244,332 / 243,832 / 254,769 -- a 4.5% spread, against the 40% spread the raw averages showed. Over that same window the accumulation slope was 832 / 808 / 792 tokens per message: monotonically DECREASING, so the later segments were marginally more efficient per turn, not less. The three segments ran 423 / 525 / 653 assistant messages (256 / 316 / 325 metrics-turns), and that difference is the entire effect.

  **The mechanism, stated exactly.** Context grows monotonically from a ~57.5K base at a near-constant rate and is never trimmed, so `avg context/turn ~= (start + end) / 2` is a LINEAR FUNCTION OF SEGMENT LENGTH. Total cache-read is `base x T + sum(delta_i x (T - i))`, which is QUADRATIC in T because every token added at turn `i` is re-read on each of the remaining `T - i` turns. Modelled against the costliest segment that gives 18,629,352 + 94,600,413 = 113,229,765 token-reads versus 112,723,268 measured (0.4% error), so the model is validated: 84% of the bill is re-reading accumulated content and 16% is the static base. One segment equals one section (`overnight-sequencer/SKILL.md:359`, rollover after every fully-shipped section), so `avg context/turn` was measuring how big the section was, never whether rollover worked.

  **What accumulates, by the tool whose result landed, on the costliest segment (522,274 tokens added, weighted by the turns that must re-read it).** Bash 290,714 raw tokens / 45.7% of re-read cost / $64.82 over 207 calls; Read 62,142 / 17.3% / $24.55 over 30 calls; Edit 83,552 / 16.6% / $23.53 over 71 calls; Skill 70,162 / 16.0% / $22.75 over 12 calls; Agent 15,091 / 4.2% / $5.96 over 3 calls. (An earlier draft of this paragraph added "and 108 of the 207 Bash calls were `bash_search`, a Grep-tool-floor violation". That was WRONG and is retracted: the follow-up determination below found 108 of those 109 are compound pipelines and exactly one is a pure search.)

  **The fix chosen on this evidence, in value order.** (1) BOUND SEGMENT LENGTH. Because cost is quadratic in T, the exact counterfactual replayed from the real trace is that the same work split across 2 sections costs 59% of the actual cache-read and across 3 sections costs 44%. Nothing else on this page is worth as much. This is NOT the retired mid-section rotation and needs no committed-but-unpushed window: it is the section SPLIT that `overnight-sequencer/SKILL.md:388` already prescribes ("a section too big for one context should be SPLIT... not rotated mid-way"), which until now had no cost calibration to size its thresholds against. (2) ATTACK THE BASH SLOPE, worth 46% of the re-read bill, where over half the calls are searches doctrine already routes elsewhere.
  **Reporting fix SHIPPED with this diagnosis.** `cost-summary.py` printed `avg context/turn` with no turn count beside it, which is what produced the wrong call; it now prints the turn count, the end-of-segment context, the accumulation rate, an explicit statement that the average scales with segment length and is not a rollover-health metric, and a per-run estimate of what splitting the section would have saved. Pinned by two new cases in `scripts/overnight/tests/test_cost_summary.py` (the caveat is present; the split estimate is omitted when there is no slope to fit it from).

- [x] **SHIPPED 2026-07-28: metrics now record the real section number, so the calibration dataset starts accumulating from the next run.**
  Determination run before starting the calibration below, and it stopped it: the `section` field was **`0` in all 56 metrics rows ever written**, across every run in `.claude/overnight/metrics/`. Nothing correlated a section to its turn count, so there was no per-section outcome data to fit a threshold against; the coarser `(run, todo)` grouping yields 21 points over about three TODO files, which is the "guess with a ~10x error bar" this file's preamble exists to prevent.
  **Root cause: nothing ever told the guard which section was being worked.** `run_phase_guard.py cursor` takes an OPTIONAL index and defaults it to the value already in state; the documented call shape in `overnight-sequencer/SKILL.md` is `cursor <domain> <file>` with no index, so `section_idx` never left the `0` that `start` initialises it to, and `stream-report.py` faithfully stamped that constant on every record. The field was not broken, it was never fed.
  **Fix: derive it deterministically instead of adding an argument the model must remember.** `cursor` now calls `_derive_section_idx()` when no index is passed, which asks the same triage oracle the sequencer routes on (`sequencer_triage.py --classify`) for the first section still classed NEEDS_WORK. Verified live against TODO-04: derives 20, matching the oracle's first NEEDS_WORK section, and an explicitly passed index still wins. Fail-open in every direction (missing oracle, non-zero exit, unparseable JSON, non-int section, all sections DONE) so a metrics field can never fail a `cursor` move and wedge a run. Covered by `scripts/overnight/tests/test_cursor_section_idx.py` (derivation, explicit-wins, three fail-open paths, helper-never-raises) and the skill's command table now documents the derivation.

- [x] **DETERMINED 2026-07-28: the `bash_search` half was NOT a Grep-tool-floor violation. The classifier over-attributes; the real Bash cost is elsewhere, and the one clean lever in it shipped.**
  The original item assumed 108 of 207 Bash calls were searches that should have been Grep-tool calls, and offered the alternative that the classifier was mis-attributing them. The second branch is correct and the first is retracted. Of the 109 calls `_SEARCH_RE` flags, **108 are compound pipelines and exactly 1 is a pure search**; the leading binaries are grep 29, `bash` 27, `sed` 20, `git` 10, `python3` 9. They are shapes like `bash scripts/build.sh 2>&1 | tail -5; echo "=== verdict:"; grep -E "error:" build/build.log`, which the Grep tool cannot express. `_SEARCH_RE` matches a search binary anywhere after `|`, `;`, `&` or a backtick, so any compound command containing a grep is labelled a search: `bash_search` is a volume counter, NOT a doctrine-compliance signal, and must not be cited as one again. The item's other assumption was also already handled: 36 of 45 build/test calls route through `run-artifact.sh` and the raw remainder is 4% of Bash.
  **Where the Bash 290,714 tokens actually go.** Codex wait/broker 61,098 (21%, n=23, avg 2,656); multi-part probe commands 59,276 (20%, n=49, avg 1,209); heredoc `python3 - <<` edit scripts 53,956 (18%, n=28, avg 1,927); everything else 116,384 (40%, n=107).
  **SHIPPED: the codex-dispatch backgrounding fix**, the one lever in that table with a clean mechanism.
  - **Split by invocation shape**, 11 broker dispatches on this segment ran `... & wait` (n=4, 19,740 result chars, avg 4,935) against `... 2>&1 | tail -N` (n=7, 5,960 chars, avg 851): 5.8x, same script, same work.
  - **Bash's job-completion notice prints the whole command line back**, and a dispatch's command line IS the 2-5 KB Codex prompt, so the prompt is paid twice and then re-read on every remaining turn. The `&` buys nothing because the broker already detaches the review into its own `systemd-run` scope and returns immediately.
  - **Bundling the kinds is NOT the alternative**: the broker header forbids it ("Never bundle several dispatches behind one opaque shell command") because per-kind gate receipts parse the command line, so the fix is one PIPED dispatch per kind.
  - **Enforced by `.claude/hooks/codex_dispatch_bg_reminder.py`**, warning-only and budgeted to 2/session on the `cd_prefix_reminder` pattern, since the backgrounded command is correct and blocking it would trade a real review for a token saving.
  **The other 79% has no identified lever and no item is filed for it**, per this file's rule that a projection is not a finding. The nearest candidate if someone picks it up is the heredoc edit scripts (18%, avg 1,927 tokens): they echo a whole multi-file edit program into context where the Edit tool would not, but whether Edit is actually cheaper for those specific multi-file rewrites is unmeasured, so determine it before acting.

## Two shipped mechanisms that were not working -- both determined 2026-07-28

Neither turned out to be the failure it was filed as. One had nothing to do; the other was never told a kind existed.

- [/] **`agent_result_cache`: determined NOT mis-keyed. All 5 dispatches were genuinely distinct work, so a correct cache would also have hit 0. Retirement needs a bigger post-fix sample.**
  Every Agent dispatch of the night was read from the three session transcripts. They were: `concurrency-evidence-mapper` on `task_exec()` in `src/kernel/sched/task.c` pre-implementation (seg 1); `kernel-explorer` mapping exec publication + staging release; `section-context-mapper` on the user-mode fault-injection harness; `kernel-quality-auditor` on the shipped diff; and `concurrency-evidence-mapper` on the shipped diff `f62f3b83..2454518f` (seg 3). Five distinct tasks. The only same-type pair is dispatch 1 vs 5, and their inputs differ substantively (a pre-implementation function inventory against a post-ship diff inventory) -- a cache that HAD hit there would have served a pre-implementation answer for a post-ship diff, which is actively wrong. So the cache behaved correctly on all five; it simply had nothing to hit.
  **Why this does not yet close as "retire".** The 155 pre-fix stores cannot be used as evidence of non-repetition, because the key was known-broken then -- their zeros are explained by the bug T2-2 fixed, not by dispatch behaviour. That leaves 5 post-fix dispatches as the entire usable sample, which is too small to retire a mechanism on. **Revisit condition: if the next ~3 nights add post-fix dispatches with still 0 hits AND spot-checking again shows all distinct, retire it** -- the hook, its state file, and its cost-summary row. Do NOT "fix" the key again without first finding two dispatches that SHOULD have matched; there is no evidence any exist.

- [x] **DETERMINED + FIXED 2026-07-28: the convergence gate was not mis-keyed. Three of four rounds were legitimately re-dispatched; the fourth exposed a real gap, now closed.**
  All four all-time `redispatch` records were read from `.claude/state/offload-events.jsonl`. Two read "no prior adversarial verdict ... first dispatch" (nothing existed to suppress -- correct). One reads "re-adversarial inputs changed since last verdict (scope: src)" (the inputs genuinely changed -- correct, and suppressing it would have skipped a needed review). So "0 of 2 suppressed" was a NON-FINDING for three of the four, exactly as this item's second branch anticipated.
  **The fourth was a real defect:** "unknown kind 'test-coverage' -- fail-open to redispatch". `KIND_SCOPES` in `review_convergence.py` listed only adversarial, re-adversarial, perf, consistency and design, and a kind absent from that table fails open FOREVER -- it cannot be fingerprinted, so the gate can never suppress it no matter how many identical rounds run. Grepping the tree for `review-kind:` found nine live spellings, so four were unscoped: `test-coverage` (6 uses), `gap-audit` (12), `performance` (2), `adversarial-impl` (1).
  **Fix:** all nine kinds are scoped, erring WIDE on purpose -- a wider scope only causes more redispatch, while a narrow one can suppress a review that was needed. The durable part is `test_every_review_kind_the_repo_uses_is_scoped`, which re-derives the vocabulary from the tree instead of hard-coding it, so the next kind someone introduces fails the suite rather than silently disabling convergence for itself (verified: an injected unknown kind is caught). Placeholders from usage strings (`[review-kind: X]`) are excluded explicitly.

## Housekeeping

- [x] **MEASURED 2026-07-28: index contamination cost ~$3.39 of a ~$509 night (0.7%). The cost angle does NOT justify the worktree; the cheap fixes are the whole answer here.**
  The item asked for the number before choosing a fix, because the strong fix (a separate `git worktree`) costs a second checkout and build directory. Scanned all three session transcripts for turns referencing a cross-sweep -- the four named commits (`46b553a3`, `5ec722df`, `a0410d3d`, `c305c165`) plus the phrases the run actually used ("HEAD moved", "operator committed", "operator's", "not mine"). Fifteen turns touched it across the night: 5 / 2 / 8 by segment. Priced at each turn's own context against the validated cache-read model, that is $1.32 + $0.58 + $1.49 = **$3.39, or 0.7% of the night**.
  **That figure is an UPPER bound and still small.** A turn was counted whole if it so much as mentioned the contamination, but several were doing other work in the same turn, so the true diagnosis-only cost is lower than $3.39. Either way it is two orders of magnitude below the 76.7% that cache-read accumulation costs, and nothing about it argues for a second checkout.
  **This closes the COST question only.** Correctness -- wrong attribution on four commits in four hours -- is a separate argument owned by `overnight-runner-improvements-v02.md`, and it is not settled by a dollar figure: a commit that claims the wrong author is wrong at any price. If the worktree is built, build it on the correctness case. What this measurement does rule out is justifying it as a token-saving move; on cost grounds the cheap fixes (explicit-path staging, `git commit -- <paths>`) are sufficient, exactly as the item anticipated.
  **Correction 2026-07-28 14:25, and it does not change the cost verdict but does change the DECISION.** A third argument surfaced on the second canary that is neither cost nor attribution: the shared tree blocks operator verification outright.
  - **The `pre-push` CI-parity gate compiles the WORKING tree**, so with a section half-written in it no operator push can pass -- a markdown-only commit was refused with `[FAIL] Build failed` against 232 lines of the run's in-flight kernel edits -- and the documented escape is `SKIP_CI_PARITY=1`, the one gate this repo keeps REQUIRED because a green local suite hid a bug for 297 commits.
  - **Operator and run also share `build/`**, so a gate run leaves a verdict in `build/build.log` that the other party is instructed to read as its own. Filed in `overnight-runner-improvements-v03.md`.
  - **So**: the cheap fixes remain sufficient for the cost angle measured here, and the worktree is now justified on workflow-blocking grounds it was not justified on before. Do not cite this item as evidence AGAINST the worktree.
