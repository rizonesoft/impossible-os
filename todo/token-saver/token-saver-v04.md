# Token Saver v04 -- 3-Day Canary Cost Findings (3-day canary, armed 2026-07-28)

Findings from the 3-day unattended canary armed 2026-07-28. This file is a CAPTURE surface, not a work queue: it sits outside the sequencer's traversal, so nothing here is implemented by the run.

**Why findings land here instead of being fixed.** The run is explicitly NOT permitted to modify its own control plane while unattended -- `.claude/hooks/**`, `.claude/skills/**`, `scripts/overnight/**`, `.githooks/**`, `.claude/settings.json`. Over three days with nobody watching, a bad edit to a gate or the sequencer skill is how a run becomes unrecoverable, and the runner suite gate runs at commit but cannot judge intent. Ordinary work is unaffected: kernel code, tests, docs and TODO files are fixed in place as normal, and the run SHOULD keep doing what it did on 2026-07-28 when it root-caused and fixed `test-smoke-matrix.sh` destroying its own leg logs.

**What to write.** One item per finding, in the house style: what was observed live (with timestamps and file:line), the mechanism confirmed at source, and what it would cost or risk. A projection is not a finding. If a fix is obvious, describe it -- do not apply it.

**Scope:** cost only. The >= 2% bar from v03 still applies -- anything measured below it is recorded as excluded, not filed as work. Runner/flow findings go to [`overnight-runner-improvements-v04.md`](../overnight-runner-improvements/overnight-runner-improvements-v04.md) instead.

**Baseline to compare against:** the 13:59 canary of 2026-07-28 -- 893 turns, $505.36, $80.64/hour, static base 58.3K, accumulation ~1,000-1,200 tok/turn. The split threshold was calibrated to `items >= 5` just before this arm, so a shift in section length distribution is expected and is the first thing to check.

## 1. Item-count splitting is necessary but not sufficient: the review loop is the real length driver

- [x] Rotate the worker context mid-section on a context threshold, not only at section boundaries
      The adversarial review loop is the natural rotation point, and the split predictor cannot see it.
  - **Observed live.** Segment `run-20260730-151719` ran 15:17:19 -> 19:05:27 (3h48m), 335 turns, **$179.27**, end-of-segment context **492,513 tokens**, accumulation ~1,123 tok/turn never trimmed.
  - **It shipped exactly ONE section** -- TODO-04 §34, via `4c3201c2` (18:23), `228b8264` (19:01), `c131e286` (19:01), `019abb90` (19:02). The per-section report attributes 330 of the 335 turns to a single segment (`sec 0`, 99,509,865 cache-read tokens).
  - **Mechanism, confirmed.** §34 had ALREADY been split by the recalibrated predictor: `d0126430` (14:40) split it into §34/§38 on the `open_items >= 5` gate at [`section-manifest.py:207`](../../scripts/overnight/section-manifest.py). The remainder still cost 330 turns.
  - **The driver was the review loop, not item count** -- the run's own closing line reports 23 findings fixed, 1 accepted with an XREF, no deferrals. Item count is a pre-implementation feature; finding count is only knowable after the review runs, so no item-count threshold at any value can predict this section.
  - **Third instance, not the first.** The calibration comment at [`section-manifest.py:204-206`](../../scripts/overnight/section-manifest.py) already recorded two sections of 352 and 379 turns carrying only 3-4 items, concluding verbatim that catching those "needs a different mechanism, not a lower number here." §34 is the third data point and the first measured end-to-end with a dollar figure.
  - **Cost.** `cost-summary.py` projects the same work split across 2 segments at ~69% of this cache-read cost ($105.69 vs $152.96) and across 3 at ~59% ($89.94): a **31-41% saving on the dominant bucket**, ~$47-63 on this segment alone. Cache-read was 85.3% of segment spend. Far above the >= 2% bar.
  - **Proposed shape.** Checkpoint and rotate when end-of-segment context crosses a threshold (~300K on this evidence), taking the rotation at a review-round boundary rather than mid-edit. A review round is the cheapest rotation point because its true input is the finding list plus the diff, not the accumulated conversation -- the state that must survive is already written down. Rotating at section boundaries only, as today, cannot help a single section that runs 330 turns.
  - **UPDATE 2026-07-30 (attended): the mechanism already exists and is switched OFF.** `rollover-wip` + `review-resolved` + the A1-A9 gates are all built and tested (`test_p45_wip_rollover.py`, `test_rotate_hint.py`); the trigger is `rotate_hint.py`, gated on `ROTATE_HINT_ENABLED = False`. It was retired 2026-07-14 (B1, Canary #2) on TWO premises, and this finding falsifies one of them: **"140 tool-events ~= one section"** against measured **334 / 420 / 768** on three consecutive 2026-07-30 segments. So the item is not "build a rotation" -- it is "un-retire one, on corrected evidence".
  - **What shipped 2026-07-30**: the falsified premise is corrected at both sites that record it (`rotate_hint.py`, sequencer SKILL) so the mechanism cannot stay retired on a number that is no longer true, and arm-readiness **A7 is closed** -- `_head_adds_ship_stamp()` now scans the cumulative `@{u}..HEAD` range instead of HEAD alone (a stamp commit followed by an unpushed fixup used to hide the stamp and let a SHIPPED section take the weaker WIP path) and returns `None` for undeterminable, which `rollover-wip` refuses, replacing a fail-OPEN that the old "the unpushed guard fail-closes too" pairing argument did not actually cover. Two regressions added; 54/54 runner suite and 876/876 tooling green.
  - **CLOSED 2026-07-30 (attended, on explicit operator instruction).** The surviving premise turned out not to be a property of the runner but of the RETIRED DOCTRINE, which never told the worker to make a mid-section WIP commit; the restored firing procedure does exactly that (a LOCAL commit, deliberately unpushed), so `_unpushed_count() > 0` is created rather than waited for. Shipped together:
    - **A8** -- `review-resolved` no longer mints a receipt for an absent/empty review state (`if rs and ...` skipped the received AND binding checks entirely when `rs` was `{}`, so a section with NO Codex review could certify a review cycle that never ran), and refuses an empty `review_run_id`.
    - **A9** -- the resolution receipt is now bound to the review round, not just HEAD. A re-adversarial round against an unchanged HEAD is routine, and the old receipt still matched on `head` alone and certified the section as resolved while a newer review sat unreceived.
    - **Doctrine + flag** -- the SECTIONS-phase firing procedure is restored (WIP-clean boundary -> `review-resolved` -> `rollover-wip` -> end turn; the watchdog resumes the SAME section from the enriched checkpoint), and `ROTATE_HINT_ENABLED = True` with `ROTATE_HINT_TURNS` re-derived from the measured ~1,123 tok/turn accumulation: the ~300K band lands at turn ~215, so **200**, which puts a typical 330-turn section at 2 segments and the 768-event outlier at 4 while staying above the ~132 events Canary #2's genuinely-short sections reached.
    - **Pinned** -- `test_rotate_hint.py` asserts the flag, the threshold AND that the SKILL still says ACTIVE, so flag and doctrine cannot drift apart; a deliberate revert must update both. 54/54 runner suite, 876/876 tooling, hook audit clean.
    - **Not yet observed in a live run.** The saving (31-41% of cache-read) is modelled, not measured end-to-end. The next canary is the proof: compare per-segment tool-events and `context/turn end-of-segment` against the 334/420/768 and 492K/542K/798K baselines above.

## 2. Zero agent dispatches and a 68% re-read rate across a 330-turn segment (OFFLOAD-MISS)

- [/] Size and close the offload miss: the router did not fire once in 330 turns, and two thirds of file reads were repeats
  - **Observed live.** Same segment: `agent dispatches: 0`; `re-reads: 24/35 (68%) over 11 distinct files`; `agent cache: 0 hits / 0 stores (n/a)`; `sec 0` flagged **OFFLOAD-MISS**. The interactive-offload doctrine routes any task costing 3+ search/read rounds or ~50 KB to an analyst; 11 distinct files re-read 24 times is that shape, and nothing was dispatched.
  - **Not yet sized.** Unlike item 1 the saving is not measured: the re-read counter records repeat reads but not their token cost, so the share of the 99.5M cache-read tokens attributable to re-reads is unknown. Attribute bytes per re-read first, then compare against the >= 2% bar. Filed as a measurement task, not a fix.
  - **Do not assume the router is broken.** `build_offload_reminder.py` was fixed 2026-07-28 (the `\b` matched the dot in `build.sh`; `_is_headless_run()` added so `_in_sections()` requires run identity). A miss after that fix may be correct: a 330-turn review loop re-reading the same 11 files it is actively editing is not obviously offloadable. Establish which before changing anything.
  - **PARTIAL 2026-07-30: the measurement was BLOCKED by missing telemetry, and that is now fixed.** Sizing needs the bytes each Read actually pulled, and `tool-history.jsonl` recorded no extent -- a `Read(offset, limit)` slice and a whole-file read were indistinguishable. The only possible estimator therefore priced every read at the file's CURRENT full size and reported re-read waste at **139.4% of the run's own cache-read**: an estimate larger than the quantity it is a share of, i.e. self-evidently invalid. Two independent over-counts caused it (slices charged as whole files; files that GREW during the segment measured at their final size).
  - **Shipped instead of a fudge factor**: `tool_history_writer.py` now records `{offset, limit, bytes}` on every Read, and `cost-summary.py` prices a re-read as `extent/4 x remaining turns` (position dominates count -- an early re-read of a large file is worth orders of magnitude more than a late one). An unsized read contributes NOTHING and is counted, so the report says "NOT SIZEABLE: 0 of 35 reads carry a byte extent" for pre-2026-07-30 runs rather than inventing a number. Four regressions pin it, including that waste can never exceed the total.
  - **Still open**: the actual number. It cannot be recovered retroactively -- the extent was never recorded -- so this stays `[/]` until the next canary produces a segment with sized reads, at which point the >= 2% comparison is a single `cost-summary.py` run.
