## Metrics that make a working system look broken

- [ ] **`review convergence: N/M rounds suppressed` counts FIRST dispatches in its denominator, so a correctly-working gate always reports 0/M on a fresh section.**
  Measured on the 13:59 canary segment: the cost summary printed `review convergence: 0/4 rounds suppressed`, which reads as a dead gate. All four `redispatch` records in `.claude/state/offload-events.jsonl` say the same thing -- **"no prior <kind> verdict for todo/00-infrastructure/TODO-04-usermode-test-framework.md#20 -- first dispatch"** -- for `design`, `adversarial`, `perf` and `re-adversarial`. Every one was the first time that kind had run against that section, so there was no recorded verdict to compare against and suppression was impossible BY DEFINITION.
  **The gate was right four times out of four and the metric reported it as 0% effective.** A convergence gate can only ever suppress a RE-dispatch of a kind that already has a recorded verdict; counting first dispatches as unsuppressed rounds guarantees a bad-looking number on every section that runs each kind once, which is the normal case.
  **This is the same defect class as the `avg context/turn` length confound fixed this morning**, and it has the same consequence: it caused a backlog item. `token-saver-v02.md` filed "Review convergence suppressed 0 of 2 rounds -- the T3-3 gate did nothing" on exactly this reading, and the determination that closed it had to go read the raw redispatch records to discover three of the four rounds were legitimately un-suppressible. Nobody should have to do that twice.
  **Fix:** exclude first-dispatch rounds from the denominator and report them separately -- e.g. `review convergence: 0 suppressed / 0 eligible (4 first dispatches)`. When `eligible` is 0 the gate had no opportunity and the line should say so rather than implying failure. `cost-summary.py` reads `converged` / `redispatch` kinds from `offload-events.jsonl`; the `detail` string already distinguishes "first dispatch" from "inputs changed", so the data needed is present and no new instrumentation is required.
  **NOT fixed during this canary:** `scripts/overnight/cost-summary.py` is FLOW-CRITICAL control plane and is one of the paths this canary is proving; editing it mid-run would make the stamp cover a reporter the run never used. Land after the stamp.

## Known limitation of the section instrumentation shipped 2026-07-28

- [ ] **The section derivation depends on an EPHEMERAL cache, so it degrades to a STALE section number rather than an obviously-missing one.**
  `run_phase_guard._derive_section_idx()` shells out to `sequencer_triage.py --classify`, which hard-fails with `FileNotFoundError: todo-graph cache not found: build/todo-cache.json`. The derivation fail-opens to `None` on that error and the cursor keeps its PREVIOUS value, which is the correct safety choice -- a metrics field must never fail a `cursor` move -- but it means a stale number is indistinguishable from a fresh one in the recorded data.
  **The cache is genuinely transient, observed 2026-07-28 16:47.** It lives under `build/`, and `scripts/todo-graph/build-and-validate.sh` DELETES it after every run unless `--keep-cache` is passed. A live probe found it absent at 16:47 and present again at 16:48 when the run rebuilt it, so the window is short but real; `build/` is also the directory shared with the operator and cleared by `build.sh clean`.
  **Severity is low and the fix should not be a block.** The previous cursor value is usually the adjacent section, so a stale record is approximately right rather than wildly wrong, and the calibration this instrumentation feeds tolerates a small amount of noise. Do NOT make the derivation fail the cursor move; that trades a metrics inaccuracy for a wedged run. Two proportionate options: have `_derive_section_idx()` rebuild the cache once on a cache-miss before giving up (it already tolerates a 60s subprocess), or record a distinct marker (`section: null` plus a `section_source: "stale"` field) so the calibration can EXCLUDE unreliable rows instead of silently averaging them in. The second is cheaper and keeps the dataset honest, which matters more here than coverage.
  Recorded against the instrumentation the same day it shipped, because a dataset whose gaps are invisible is the failure mode this whole file exists to catch.

## Commit-side analogue of the push-side block (fifth facet of the shared tree)

- [ ] **The pre-commit lint requires a graph cache fresh against `todo/**/*.md`, so an operator cannot commit a TODO change while the run is editing TODOs.**
  Hit live 2026-07-28 16:49 attempting to commit this very file: `error: Check 7 (stub-behind-stamp) cache stale relative to todo/**/*.md; rebuild with bash scripts/todo-graph/build-and-validate.sh and re-run lint`. The staleness was not caused by the commit -- it was caused by the RUN editing `todo/00-infrastructure/TODO-04...md` and `todo/02-kernel-core/TODO-21...md` seconds earlier. The operator's change was a new file in a different directory.
  **The prescribed remedy is unsafe while a run is active.** Rebuilding the cache writes `build/todo-cache.json`, which the run's triage oracle reads and which `sequencer_triage.py` hard-fails without; doing it mid-run races the run's own rebuild and mutates shared state the run depends on for routing. So the operator's only safe options are to wait for a quiet window or to leave the work uncommitted -- and leaving it uncommitted is what lets the run's `git add -A` sweep it, which is the v02 contamination finding. **The two safety rules genuinely conflict**, exactly as `overnight-runner-improvements-v02.md` predicted when it wrote "never leave work uncommitted while the run is active, and never commit while it has files staged. Those two rules conflict, which is itself the argument for the worktree split."
  **This completes the picture: FIVE independent facets of one shared tree**, all observed on the same day -- (1) the index, giving cross-swept commits; (2) the working tree, making the pre-push CI-parity gate compile the run's half-written code; (3) `build/`, letting one party's verdict be read as the other's; (4) the hook control state, so an operator session inherits the run's phase gates; (5) the graph cache, blocking operator TODO commits. Every one of them is removed by giving the run its own `git worktree`, and none of them is removed by any cheaper fix. The cost measurement in v02 (0.7% of a night) remains the correct answer to the question it asked and the wrong basis for this decision.

- [ ] **INCIDENT 2026-07-28 17:32: the operator's single uncommitted TODO file REFUSED the run's rollover. The hazard above is not theoretical.**
  This session wrote a finding into `todo/token-saver/token-saver-v03.md` at 16:49 and could not commit it, because the pre-commit lint demanded a graph cache fresh against `todo/**/*.md` that the RUN was invalidating with its own edits (the item above). The file therefore sat uncommitted. At 17:32:04 the run committed its own work, leaving the operator's file as the ONLY dirty path in the tree, attempted its verified rollover, and was **"refused on two counts"** -- `_dirty_owner` correctly classifies a prose edit to a `todo/*.md` as `tracked-source`, which blocks. The operator had become the blocker.
  **Both available remedies were themselves hazards, which is the whole point.** Committing would have moved HEAD while the run was mid-receipt-generation (it started build/test/smoke at 17:32:29), invalidating the content-bound receipts it was paying for and causing a further spurious refusal. Rebuilding the graph cache to satisfy the lint would have raced the run's routing oracle. The resolution used was to REMOVE the file from the tree entirely (preserved out-of-tree, restored later), which clears the block without touching HEAD or shared state -- but that is a workaround an operator has to know, under time pressure, while a run stalls.
  **Recorded against this session's own conduct, deliberately.** Every rule was followed: explicit pathspecs, no `git add -A`, commits held during the receipt window, no mid-canary control-plane edits. The block happened anyway, from writing ONE markdown file in a directory the run never touched. That is the strongest available evidence that the cheap fixes cannot close this class and the worktree split is the actual answer -- careful operation is not sufficient when the tree itself is the shared resource.
