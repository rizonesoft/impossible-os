# TODO-07 -- LSP to MCP Bridge

> **Goal:** Build a host-side MCP server that proxies five language servers -- clangd (C/H), asm-lsp (NASM), bash-language-server (.sh), pyright (.py), PowerShellEditorServices (.ps1) -- and exposes their capabilities (hover, go-to-definition, find-references, diagnostics, workspace-symbol, document-symbol, code-actions) as six read-only MCP tools. Lets Claude Code, Cursor, Aider, and any MCP-aware agent get compiler-grade code intelligence across every language the repo uses, instead of falling back to grep-and-hope.

> [!IMPORTANT]
> **Current state:** `clangd-19` is installed per [TODO-01 §1](./TODO-01-developer-tooling-stack.md#1-host-bootstrap-and-dependency-contract) and `compile_commands.json` is generated by `bear` during `scripts/build.sh clean`. A VS Code user with the `llvm-vs-code-extensions.vscode-clangd` extension gets full C intelligence interactively -- but Claude Code, Cursor, and every other MCP-based AI agent cannot call clangd: the protocols are incompatible and trying to register clangd itself as an MCP server hangs the harness (pinned in [docs/infrastructure/development-tooling.md:699-700](../../docs/infrastructure/development-tooling.md#L699-L700) and [:1008](../../docs/infrastructure/development-tooling.md#L1008)). No LSP is active for `.asm`, `.sh`, `.py`, or `.ps1` at all; agents rely on grep and file reads. The existing [TODO-06 §8](./TODO-06-todo-metadata-layer.md#8-mcp-server-ai-agent-transport-over-the-cache) MCP server for `todo-graph` establishes the FastMCP-in-Python + `.claude/mcp.json` stdio-subprocess pattern this bridge will reuse.

## Outcome

- Single MCP server `scripts/lsp-mcp/bridge.py` that spawns up to five LSP subprocesses on demand and exposes six read-only MCP tools: `hover`, `definition`, `references`, `diagnostics`, `workspace-symbol`, `document-symbol`. Each tool takes a `path` argument (used to route to the correct LSP by extension) and tool-specific params (position, query string).
- Language coverage wired and self-tested: clangd for `.c`/`.h`, asm-lsp for `.asm`, bash-language-server for `.sh`, pyright for `.py`, PowerShellEditorServices for `.ps1`. Missing optional deps -> `SKIP` with structured error, never hang or crash.
- `.claude/mcp.json` lists `lsp-bridge` alongside `todo-graph`; Claude Code auto-registers it. `python3 scripts/lsp-mcp/bridge.py --self-test` exits 0 with a manifest of which LSPs were detected and which tools are live.
- Setup-deps, manifest, Makefile target, and `docs/infrastructure/development-tooling.md` subsection updated in the same PR as the code; `scripts/test-tooling.sh` includes surface checks (harness exists, `--help` exits 0, `--self-test` exits 0, manifests well-formed).
- Boundary compliance verified: repo-tracked manifest lists only read-only tools; no write-capable LSP methods (`textDocument/rename`, `textDocument/codeAction` with execute, `workspace/applyEdit`) are reachable from MCP.
- Extended tool surface (§11): completion, signature help, type-definition, implementation, declaration, call hierarchy (incoming/outgoing), read-only code_action -- matches every production LSP-MCP bridge without breaching the read-only boundary.
- Robustness: file-change lifecycle forwarding (§12) keeps LSP views fresh across parallel editing; per-LSP watchdog + auto-restart (§13) transparently recovers from child crashes with exponential backoff.
- Observability + security + performance: JSON-lines logs with correlation IDs threaded MCP->LSP->MCP (§14); workspace-bounded path sandboxing rejects escape attempts (§15); opt-in `--warm-start` bounds first-call latency (§16).

## 1. Bridge Skeleton + LSP JSON-RPC Client

Lay down the process skeleton, the FastMCP server, and a minimal LSP JSON-RPC client that speaks LSP over stdio to a spawned subprocess. This is the foundation every language integration builds on.

- [x] Create `scripts/lsp-mcp/bridge.py` with FastMCP server, `--self-test` flag, and module-level `_CALL_LOCK` (pattern from [`mcp_server.py`](../../scripts/todo-graph/mcp_server.py)).
- [x] Create `scripts/lsp-mcp/lsp_client.py` implementing minimal LSP JSON-RPC 2.0: `initialize`, `initialized`, `textDocument/didOpen`, `shutdown`, `exit`, plus request/response correlation via `id` field and header framing (`Content-Length:` + double CRLF).
- [x] Implement `LspSubprocess` class: spawn via `subprocess.Popen` with stdin/stdout pipes, reader thread draining stdout, separate stderr drain thread (prevents LSP stderr log pipe from filling and deadlocking a running child), timeout-based shutdown with SIGTERM->SIGKILL escalation, cleanup on bridge exit via `atexit` + `weakref.WeakSet`.
- [x] On-demand lifecycle: LSPs are NOT spawned at bridge startup; first request for a given language spawns that LSP and caches the handle. Prevents idle overhead when an agent never touches a language. Registry seeded via `register_spawner()` hook; empty in this skeleton (per-language recipes land with §2-§6).
- [x] JSON error envelope on any LSP failure (timeout, subprocess crash, unsupported method), matching `mcp_server.py`'s pattern -- never let an LSP error become an MCP exception. Envelope reserves `error` + `detail` keys against `extra`-dict poisoning.
- [x] Commit: `"scripts/lsp-mcp: bridge skeleton + LSP JSON-RPC client"`

**Test checkpoint:** `python3 scripts/lsp-mcp/bridge.py --self-test` exits 0 and prints `[lsp-mcp] OK: 0 LSPs spawned, bridge ready`. FastMCP tool registry shows 0 tools (tools come in §7). Manual import: `from scripts.lsp_mcp.lsp_client import LspSubprocess; c = LspSubprocess(['cat'], lang='test'); c.shutdown()` completes without leaking the subprocess (`pgrep cat` empty after). No `boot` / kernel / POST16 involvement -- this is host-side Python tooling.

## 7. Six MCP Tools (Hover, Definition, References, Diagnostics, Workspace/Document Symbol)

Expose six typed MCP tools. Each tool dispatches to the right LSP based on file extension from the `path` arg, issues the LSP request, and returns a normalized JSON response. > [!IMPORTANT]
> **Read-only surface only.** DO NOT expose `textDocument/rename`, `textDocument/codeAction` execute, `workspace/applyEdit`, or any method that mutates files. The autonomous-agent boundary in [TODO-02 §8](./TODO-02-ai-development-system.md#8-autonomous-agent-boundary-policy) classifies write-capable MCP servers as forbidden. Even the `code-action` tool (if added later) must return the action list without executing.

> [!WARNING]
> **LSP-miss fallback discipline.** An empty LSP response does NOT mean the symbol does not exist. LSP only sees files in the build graph (178 compile-commands entries today) and skips `#if 0` / preprocessor-excluded branches and generated headers. Agents using these tools must compose tiers, not treat tier 1 as ground truth:
>
> 1. **LSP first** (this bridge) -- fastest + most precise for C/H/asm/sh/py/ps1 on files in the build graph. Types, macros, cross-TU references.
> 2. **`rg -n 'symbol_name' src/ include/`** via Bash -- covers every file (including non-code, generated headers, `#if 0` blocks, files not in compile_commands). Fresh on every call.
> 3. **`git log --all -S 'symbol_name'`** (pickaxe) -- finds deleted, renamed, or moved code that tier 1 + 2 missed because it's no longer at HEAD.
> 4. **Direct Read of `specs/` / `docs/` / `todo/`** -- for conceptual or prose queries that textual search can't answer.
>
> Document this chain in the §9 docs subsection so agents coming to the bridge fresh understand tier 1 is a probe, not an oracle.

- [ ] Register `hover(path: str, line: int, character: int)` -- LSP `textDocument/hover`. Normalizes `MarkupContent` / legacy `string[]` response into a flat markdown string.
- [ ] Register `definition(path: str, line: int, character: int)` -- LSP `textDocument/definition`. Returns list of `{uri, range}` dicts.
- [ ] Register `references(path: str, line: int, character: int, include_declaration: bool = true)` -- LSP `textDocument/references`.

## 8. Extension Routing, Per-LSP Lock, Concurrent-Call Safety

FastMCP dispatches concurrent tool calls. Even with the bridge-level `_CALL_LOCK`, per-LSP state (pending request IDs, cached diagnostics) needs finer serialization -- and the LSP-initialize handshake must NOT race against first-request-for-a-language. Codex flagged exactly this pattern for `todo-graph` in [TODO-06 §8](./TODO-06-todo-metadata-layer.md#8-mcp-server-ai-agent-transport-over-the-cache) (pass 17, H finding); this section applies the same fix proactively.

- [ ] Implement per-LSP `threading.Lock` inside `LspSubprocess` -- every JSON-RPC request/response cycle takes the lock. Per-LSP, not global, so requests to different LSPs can run in parallel.
- [ ] Implement one-shot `initialized` gate: first request for a language spawns + handshakes under a language-specific init lock; subsequent requests fast-path past the gate.
- [ ] Request-ID correlation: each request gets a monotonic ID; response reader thread demultiplexes via a `dict[int, Future]`. Prevents two in-flight requests from swapping replies.
- [ ] Timeout per request (default 5s, configurable via env `LSP_MCP_TIMEOUT`); on timeout, log and return JSON error envelope -- do NOT kill the LSP (it may recover).
- [ ] Extension router: `dispatch(path) -> LspSubprocess` reads file extension, returns the cached or freshly-spawned LSP, raises `JsonErrorEnvelope("unsupported extension", path=...)` if no LSP covers the extension.
- [ ] Commit: `"scripts/lsp-mcp: extension routing + per-LSP serialization"`

## 17. Scale Roadmap (Deferred)

> [!NOTE]
> **This section is not active work.** It captures the partitioning strategy the bridge will need when the repo grows past the thresholds where single-clangd-per-workspace stops working. Stated explicitly so the architectural shape is not rediscovered under pressure at 2 AM in 2029. No code ships until a trigger below fires.

Current repo is ~215k core LOC (~189k kernel + ~24k tooling per [COUNT.md](../../COUNT.md)). Single-workspace clangd is fine here and will remain fine for ~10x growth. This section plans for the regime where it stops being fine.

**Deferral triggers -- revisit §17 when ANY of these fire:**

- Total core LOC (kernel + userland + tooling, per `COUNT.md` "Core code + tooling") crosses **2,000,000**.
- `clangd-19 --check=src/kernel/main.c` on a **cold cache** takes longer than **5 minutes** (current: ~83 ms, so there's five orders of magnitude of headroom).
- `compile_commands.json` grows past **10,000 entries** (current: 178).
- An agent or human reports that `workspace/symbol` queries via the MCP bridge take longer than **2 seconds** on a warm index.
- Any single `clangd-19` RSS exceeds **4 GiB** during normal use.

**Planned shape when triggers fire (sketch, not a commitment):**

- **Per-subtree partitioning.** Spawn one `clangd-19 --compile-commands-dir=<subtree>` per major subsystem (`src/kernel/`, `src/desktop/`, `src/apps/`, `user/`) instead of one process for the whole repo. Each clangd indexes only its subtree; cross-subtree queries either federate (bridge routes the query to all clangd instances and merges) or explicitly constrain to a subsystem.
- **Bridge routing by subsystem.** Add an optional `subsystem: Optional[str]` argument to the six MCP tools (§7). Without it, the bridge queries all clangds under `_CALL_LOCK` and merges; with it, routes to one. Falls back cleanly if the single-workspace mode (the §1-§10 mode we're shipping now) is still sufficient.
- **Remote clangd-index-server.** LLVM ships `clangd-indexer` that writes a shared index to disk ([clangd remote-index docs](https://clangd.llvm.org/guides/remote-index)). A persistent background process rebuilds the index incrementally; clangd instances consume it via `--remote-index-address`. Eliminates cold-index cost on every editor restart.
- **`ccls` as fallback.** If clangd's scale limits get hit in an unfixable way, `ccls` has historically handled LLVM-class codebases better due to a different on-disk index format. Evaluate side-by-side before committing. Would require bridge adapter work but not a full rewrite -- the LSP wire protocol is identical.
- **Per-language per-subsystem caching.** `pyright` scales via `pyrightconfig.json` with `include` narrowing; `asm-lsp` is stateless; `bash-language-server` has no scale issues at our likely bash volume; PSES has known scale issues but our `.ps1` surface is small enough that it won't matter at 2M LOC of C.
